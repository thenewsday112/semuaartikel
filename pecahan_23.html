#10201. Agent Memory That Earns Its Keep

Originally published at Trida AI.

When should an agent forget that you switched suppliers?

Picture a procurement agent in its fourth month of work. It knows your main vendor well by now. It also still knows the previous vendor's payment terms, the approver who left in spring, and a delivery address from a one-off order in February, and it treats all of it as equally current. Nothing in that memory is fabricated. Every entry was true when it was written. The failure is quieter than a hallucination: the agent remembers accurately, and acts on facts whose time has passed.

That is the normal failure mode of agent memory, and it arrives because the first version worked. Remembering helped, so the team let the agent remember more, with no rule for what expires. Storing was never the hard part. The hard part is the editing: what gets in, how long it stays, and how it leaves.

Run state is not memory

Start by separating two things that often get built as one. Run state belongs to a single thread: the messages so far, the intermediate results, where this run has got to. It exists so this run can continue, and when the run ends, most of it should end too. Memory is what crosses threads. It is read in a later session, by a later run, and it changes how that run behaves.

LangGraph draws the line in exactly those terms: short-term memory is thread-scoped and persisted so a thread can resume, while long-term memory lives in a separate store, organised by namespace, and can be recalled in any thread. The distinction sounds like plumbing. It is actually a gate. If a detail only matters inside this run, it is state, and it should die with the run. Only a detail that should change a future run's behaviour earns a place in memory, and that bar should be high, because everything past it becomes a standing instruction your future self never re-read.

Three kinds of memory, three shelf lives

What passes the gate comes in three kinds, and they age differently.

Facts about a user, a vendor, an account: call this semantic memory. A preferred invoice format, a plant's shutdown week, who approves spend above a threshold. Facts are the most useful kind and the fastest to rot, because the world they describe keeps moving. An experience is different. Episodic memory holds what happened: the extraction that failed because a field was blank, the escalation that worked. Episodes age more slowly, and their value is as examples, a record of what this situation looked like last time. The third kind is procedural: the instructions the agent runs under. When an agent revises its own instructions from feedback, it is editing the rules, not the record, and that deserves a review gate the other two kinds do not need. A wrong fact misleads one run. A wrong rule misleads every run after it.

How agent memory earns its keep: a session sends candidate memories through a write gate that checks type, owner and expiry; approved entries land in a scoped memory store holding facts, episodes and instructions; a later session retrieves only what the current task needs and pages it into context; corrections and deletions flow back to the store.

Writing is the hard part

Retrieval gets the attention, but the quality of a memory system is set at write time. Two choices decide most of it.

The first is when the writing happens. Writing in the hot path, during the run, makes a memory available immediately and lets you show the user what was saved. It also makes the agent do two jobs at once, and the second job gets done badly at busy moments. Writing in the background keeps the run fast and lets a separate pass distil properly, but a second thread can start before the first thread's lessons exist. There is no free option here. Pick per deployment, and know which cost you accepted.

The second choice is shape. A single profile document, updated in place, is easy to read back whole and hard to update safely as it grows; each rewrite risks quietly dropping a field. A collection of small, separate memories is easier to add to and tends to recall better, but now the system has to update and delete entries rather than only appending, and search has to find the right one. Either way, store the distilled entry, not the transcript it came from. A transcript is a log. A memory should read like a note the agent wrote to its future self: the fact, who it belongs to, where it came from, and when it stops being safe to trust.

One vendor, three sessions

Take the procurement agent again, this time with those rules in place.

One vendor fact across three sessions: a correction in the first session is written as a scoped memory with provenance, a new thread retrieves it in the second session and the invoice passes without re-asking, and in the third session a change of details updates the memory and retires the old one.

In the first session, a person corrects the agent: this vendor's invoices are rejected unless the purchase order number sits on the first line. The correction is written as a fact, scoped to that vendor, with the session it came from attached. In a new thread weeks later, the agent retrieves the fact before processing the next invoice, places the number correctly, and nobody is asked a question they already answered. In the third session, the vendor changes its invoicing portal and the old instruction stops applying. The person says so once. The memory is updated, the old entry is retired rather than left to compete with the new one, and the next run never sees it.

Read that sequence again and notice what did the work. Not the store. The scope, the provenance, and the retirement did.

The reading side has to be just as deliberate. The useful pattern is old: MemGPT treated the context window as main memory and everything else as external storage, paging information in and out instead of pretending the window could hold a lifetime of interaction. In Claude Managed Agents, memory stores are collections of text documents mounted into the session, so the agent reads what it needs with ordinary file tools rather than receiving its whole past in the prompt. That shape matters. An agent handed fifty retrieved memories per task has not been given a memory; it has been given a distraction with a search index. Retrieve narrowly, by scope first and similarity second.

When remembering is the wrong call

Some deployments should have little long-term memory, or none. A one-shot extraction over a document set gains nothing from remembering the last client's documents, and in a multi-tenant system a namespace mistake is not a bug with an error message; it is one customer's facts surfacing in another customer's session. Sensitive detail raises the stakes again. A memory system that cannot truly delete is a liability: in the Claude Managed Agents design, every change creates an immutable version, and the redact operation exists precisely so a leaked secret or a piece of personal data can be scrubbed from history while the audit trail survives. If your stack cannot do the equivalent, be honest about it and store less.

A delete button is not enough. Forgetting also needs a clock. Facts should carry review dates tied to how fast their subject changes: an approver's name gets months, a price gets weeks, a regulatory deadline gets checked against its source. A memory with no expiry and no owner will outlive its truth, and it will do so confidently, in fluent prose, inside a session whose user has no reason to doubt it.

So the test we would apply to any memory feature is simple to state and awkward to pass. Show the write rule, the scope, the expiry, and the correction path. If a team can show all four, their agent's memory will probably earn its keep. If the answer is "it remembers everything," you are looking at next quarter's incident, already written down and waiting to be retrieved.

#10202. How to Check Failed Login Attempts on Windows 10 and 11 (Event ID 4625)

To check failed login attempts on Windows 10 or 11, open Event Viewer as an administrator, go to Windows Logs > Security, choose Filter Current Log and enter Event ID 4625. Every 4625 entry is one failed sign-in, and it tells you which account was tried, how (the logon type), why it failed (the status code) and which computer or IP address it came from. If the list is empty, check that failure auditing is switched on with auditpol /get /subcategory:"Logon".

Maybe you just want to know whether anyone has been trying their luck while you were away. Windows keeps a record, and it's far more detailed than most people expect. Below, you'll confirm Windows is recording failures, find them, then decode each field so you can tell a typo from a real problem.

Check that Windows is recording failed sign-ins

Windows only logs a failed sign-in if the Audit Logon policy is set to record failures. The good news is that you probably don't need to change anything. According to Microsoft's audit policy recommendations, Audit Logon has been enabled for both success and failure by default since Windows 10 version 1809. Older versions recorded successes only.

To confirm:

  1. Press the Windows key, type cmd, right-click Command Prompt and choose Run as administrator.
  2. Run the command below.
  3. Look at the line for Logon. 
auditpol /get /subcategory:"Logon"

System audit policy
Category/Subcategory                      Setting
Logon/Logoff
  Logon                                   Success and Failure

If it says Success or No Auditing, switch failures on:

auditpol /set /subcategory:"Logon" /success:enable /failure:enable

This works on Windows Home too, which lacks the Local Security Policy editor older guides mention. Subcategory names are translated on non-English Windows, and auditing only records attempts from the moment it's on.

How to find failed login attempts in Event Viewer

Event Viewer is built into every edition of Windows 10 and 11. The Security log needs administrator rights, so open it from an admin account.

  1. Press Windows + R, type eventvwr.msc and press Enter. (You can also right-click Start and choose Event Viewer.)
  2. In the left pane, expand Windows Logs and click Security. If you see "Access is denied", close it and run Event Viewer as administrator.
  3. In the right-hand Actions pane, click Filter Current Log.
  4. In the box that says , type 4625.
  5. Set Logged to a sensible window, such as Last 7 days, and click OK.
  6. Click any event and read the General tab underneath, or double-click it for a bigger window.

To see successful sign-ins alongside the failures, type 4624,4625 instead. That's useful for spotting a failure followed shortly by a success from the same place, which is the pattern that deserves the closest look. Microsoft's Event 4625 reference documents every field in the event.

Filtering never deletes anything; Clear Filter takes you back to the full log.

What each field in a 4625 event tells you

Only a handful of fields matter for a home or small-office check.

Field Where it appears What it tells you
Account Name Account For Which Logon Failed The user name someone typed or a program tried
Logon Type Logon Information How the attempt was made: at the keyboard, over the network, by Remote Desktop and so on
Failure Reason, Status, Sub Status Failure Information Why Windows refused it, such as a bad password or a locked account
Caller Process Name Process Information The program that made the attempt, for example winlogon.exe for the sign-in screen
Workstation Name Network Information The name of the computer the attempt came from
Source Network Address Network Information The IP address it came from. 127.0.0.1 or ::1 means this computer itself

Read them together. Logon Type 2, winlogon.exe and 127.0.0.1 is someone at the sign-in screen. Type 3 with another IP address on your network is a device trying to connect, often to a shared folder.

Logon types: how the attempt was made

The Logon Type number is the quickest way to tell where an attempt came from. These are the values Microsoft documents, with what they usually mean on a personal or small-business PC.

Type Name What it usually means
2 Interactive Someone typed a password at this computer's sign-in screen
3 Network Another device tried to reach this PC over the network, such as a shared folder or printer
4 Batch A scheduled task tried to run with saved credentials
5 Service A Windows service tried to start under an account whose password may have changed
7 Unlock Someone tried to unlock a locked screen
10 RemoteInteractive A Remote Desktop sign-in attempt
11 CachedInteractive A sign-in checked against credentials stored on the PC, common on work laptops away from the office

Types 4 and 5 usually point to a program with an old saved password, not a person.

Status codes: why the sign-in failed

The Failure Reason line gives a plain-English summary, but the hexadecimal Status and Sub Status codes are more precise. When Status is the general 0xC000006D, the Sub Status tells you the real reason. These are the codes Microsoft lists in its monitoring guidance for this event.

Code Meaning Worth worrying about?
0xC000006A Correct user name, wrong password One or two are typos. Dozens in a row are guessing
0xC0000064 The user name doesn't exist Repeated ones suggest someone trying common names
0xC000006D Bad user name or authentication information Check the Sub Status for detail
0xC0000234 The account is locked out Yes, if you didn't lock it yourself with typos
0xC0000072 The account is disabled Someone is trying an account you switched off
0xC000015B The account isn't allowed this type of sign-in Often a standard user trying Remote Desktop

A run of 0xC0000064 events with names like admin, administrator or user is the classic sign of an automated tool working through a list, because none of those are real accounts on a typical home PC.

How to check failed logins with PowerShell

Event Viewer is fine for a quick look, but PowerShell turns a week of events into a tidy table in seconds. Open Terminal (Admin) or Windows PowerShell (Admin) from the Start button's right-click menu, then paste this:

$f = Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4625; StartTime=(Get-Date).AddDays(-7)} |
  Select-Object TimeCreated,
    @{n='Account';     e={$_.Properties[5].Value}},
    @{n='LogonType';   e={$_.Properties[10].Value}},
    @{n='SubStatus';   e={'0x{0:X8}' -f $_.Properties[9].Value}},
    @{n='Workstation'; e={$_.Properties[13].Value}},
    @{n='SourceIP';    e={$_.Properties[19].Value}}
$f | Format-Table -AutoSize

The numbers in square brackets pick fields in the order Windows stores them (5 is the account, 19 the source IP). Change -7 to look further back.

To see who is trying most often, group the results:

$f | Group-Object SourceIP | Sort-Object Count -Descending | Select-Object Count, Name

What's normal and what deserves a closer look

Most failed sign-ins are harmless.

  • Probably nothing: one or two Type 2 or Type 7 failures with 0xC000006A at times you were using the PC. That's you mistyping.
  • An annoyance, not an attack: a steady drip of Type 3, 4 or 5 failures for your own account, often from another device on your network. A phone, NAS, old laptop or scheduled task is still using a password you've since changed. Update the saved password on that device and the failures stop.
  • Worth investigating: failures at times nobody was home, failures for user names that don't exist, or Type 3 and Type 10 attempts from IP addresses you don't recognise.
  • Act now: many failures followed by a 4624 success from the same source, or a 1102 event you can't explain.

If you see Type 10 attempts, check whether Remote Desktop is switched on under Settings > System > Remote Desktop, and turn it off if you don't use it. Windows Home can't host Remote Desktop sessions at all. Network attempts from outside your home usually mean something is reachable that shouldn't be, so it's worth learning how to check open ports on the same PC.

How Windows limits password guessing

Account lockout locks an account for a while after a set number of wrong passwords, which makes guessing very slow.

Microsoft's KB5020282 support article explains that new Windows 11 version 22H2 installations, and new PCs set up with the October 2022 updates already applied, get a default of 10 failed attempts within 10 minutes causing a 10-minute lockout. There's an important detail: this lockout applies to network sign-ins such as Remote Desktop. Console sign-ins at the keyboard are still allowed during the lockout period. PCs that were set up earlier and updated later don't get these settings automatically.

If you think someone is trying to get in

Failed attempts mean the password held. Work through these steps:

  1. Write down the times, account names, logon types and source addresses from the events, or save the filtered view with Save Filtered Log File As in Event Viewer.
  2. Check for any 4624 success from the same source just after the failures.
  3. Change the password for the targeted account to something long and unique. My free password generator runs entirely in your browser and can produce a three-random-words passphrase.
  4. Turn off Remote Desktop, file sharing or anything else that allows network sign-ins you don't need.
  5. Make sure Windows Update and Microsoft Defender are current, then run a full scan.
  6. If attempts came from another device on your network that you don't own, change your Wi-Fi password and review which devices are connected to your router.

If an attempt succeeded and it wasn't you, disconnect the PC from the internet and get help before using it for banking or email.

The Security log only covers sign-ins to this PC. If you sign in to Windows with a Microsoft account, attempts made online, through Outlook.com or any Microsoft website, are recorded by Microsoft instead.

  1. Go to account.microsoft.com/security and sign in.
  2. Open your sign-in activity.
  3. Look for entries labelled Incorrect password entered or an Unusual activity section.
  4. Expand anything you don't recognise to see its location, device and IP address.

Frequently asked questions

Where are failed login attempts stored in Windows?

They're stored in the Security event log, which lives at C:\Windows\System32\winevt\Logs\Security.evtx. Don't open the file directly. Use Event Viewer or PowerShell's Get-WinEvent, both of which need administrator rights to read it.

Can I see failed logins on Windows 11 Home?

Yes. Event Viewer, PowerShell and the auditpol command are all included in Windows 11 Home. What Home lacks is the Local Security Policy editor, so use auditpol from an admin Command Prompt if you need to switch failure auditing on.

Why can't I find any 4625 events?

Usually for one of three reasons: nobody has failed to sign in during the period you filtered, failure auditing was switched off, or older events were overwritten when the log reached its size limit. Run auditpol /get /subcategory:"Logon" to rule out the second one.

What does logon type 3 mean in event 4625?

Type 3 is a network sign-in. Another device tried to connect to this PC, most often to a shared folder or printer. Repeated Type 3 failures for your own account usually come from a device still using an old saved password.

Does Windows lock you out after too many wrong passwords?

It can. New Windows 11 22H2 installations default to locking an account for 10 minutes after 10 failed attempts within 10 minutes, but Microsoft says that lockout applies to network sign-ins such as Remote Desktop, not to the keyboard. Run net accounts to see your PC's actual setting.

How long does Windows keep the Security log?

There's no fixed number of days. The log has a maximum size and overwrites the oldest events once it's full. Run wevtutil gl Security in an admin Command Prompt to see the maxSize value in bytes, and save events you want to keep.

Is it safe to clear the Security log?

You can, but there's rarely a good reason to. Clearing it destroys the evidence you'd need if something went wrong, and Windows records event 1102 when the log is cleared, so an unexpected 1102 is itself a warning sign.

#10205. The Privacy Cost of "Free" Online File Converters

Search for "merge PDF" or "compress image" and you will find dozens of free websites ready to help. Drag, drop, download, done. It is so convenient that most people never ask the obvious question: where did my file just go?

For a holiday photo, maybe it does not matter. For a passport scan, an employment contract, a medical report or a bank statement, it matters a lot.

How most free converters work

The typical flow is simple:

  1. Your file is uploaded to the provider's server.
  2. The server processes it.
  3. You download the result.
  4. The provider, ideally, deletes both copies after some time.

Step 4 is where trust comes in. Privacy policies often say files are deleted after one hour, or 24 hours, or "periodically". You have no way to verify that. Files may also pass through third-party cloud storage, logging systems and backups.

What can go wrong

  • Retention beyond what is promised. Backups and logs can keep data far longer than the headline deletion window.
  • Breaches. Any server storing files, even briefly, is a target.
  • Jurisdiction. Your file may be processed in a country with different data protection laws.
  • Business model drift. "Free" services need revenue. Policies change, companies get acquired, and data becomes an asset.
  • Compliance exposure. Employees uploading client documents to random tools can create GDPR, HIPAA or contractual problems for their employer.

None of this means every converter is malicious. Most are probably fine. But "probably fine" is a weak standard for sensitive documents.

The alternative: processing in the browser

Modern browsers are powerful. With JavaScript and WebAssembly, many file operations can run entirely on your device:

  • merging, splitting and reordering PDF pages
  • laying out multiple pages per sheet
  • compressing, resizing, cropping and converting images
  • extracting tables from text-based PDFs

In this model, the website delivers the code, and your computer does the work. The file never leaves your machine.

Several tools now take this approach. FileOtter, for example, offers PDF merge, split, 2-up/4-up layout, PDF to Excel, plus image compression, cropping and format conversion, all processed locally with no upload and no account.

Trust, but verify

You do not have to take any website's word for it. Here is a two-minute check:

  1. Open the tool in Chrome, Firefox or Edge.
  2. Press F12 to open Developer Tools and select the Network tab.
  3. Process a test file.
  4. Look for a large outgoing request roughly the size of your file.

If none appears, the processing is local. For extra certainty, disconnect from the internet after the page loads and try again. A truly client-side tool will keep working.

The trade-offs

Local processing is not magic. It has limits:

  • Device power. Very large files can be slow on older phones or laptops.
  • Heavy operations. Aggressive PDF compression or OCR on scanned documents is harder to do well in a browser.
  • Feature depth. Server tools can sometimes offer more advanced options.

For the everyday tasks most people need, these limits rarely matter.

A simple rule for individuals and teams

  • Public or trivial files: Use whatever tool you like.
  • Personal or confidential files: Use local tools, either desktop software or verified browser-based ones.
  • Regulated data: Follow your organisation's approved tools list, and if there is none, ask for one.

Conclusion

The convenience of free online converters has trained us to upload first and think later. As browsers grow more capable, that trade-off is no longer necessary for most tasks. Next time you reach for a file tool, take ten seconds to ask where your file is going, and choose one that keeps it where it belongs: on your device.

#10207. Debouncing: The Tiny Hardware Problem That Haunts Every Click, Keypress and Button

Every physical button you have ever pressed lies a little. When metal contacts inside a switch close, they do not make one clean connection. They bounce, rapidly touching and separating for a few milliseconds before settling. To a fast enough circuit, one press looks like several. This phenomenon, called contact bounce, is why engineers write debounce logic, and why your old mouse may suddenly start double-clicking on its own.

What bounce looks like

If you put an oscilloscope on a mechanical switch, a single press shows a jagged burst of on/off transitions lasting anywhere from under 1 ms to over 10 ms, depending on the switch, its age and its condition. Release often bounces too.

A microcontroller sampling every few microseconds would happily report five presses where a human made one.

Debouncing strategies

Engineers handle this in hardware, software or both.

Hardware debouncing

  • RC filter + Schmitt trigger: A resistorâ€“capacitor network smooths the signal, and a Schmitt trigger converts it back into a clean edge.
  • SR latch with an SPDT switch: A setâ€“reset latch locks the first contact, making later bounce irrelevant.

These approaches are robust but add components and cost.

Software debouncing

Most modern devices debounce in firmware. Common approaches:

1. Delay after the first edge (eager):

if (pin_changed && (now - last_change) > DEBOUNCE_MS) {
    report_event();
    last_change = now;
}

This is fast to respond, but noise can trigger it.

2. Wait for a stable state (deferred):

if (raw != stable) {
    if (++count >= STABLE_SAMPLES) { stable = raw; report_event(); count = 0; }
} else {
    count = 0;
}

This is more reliable, but it adds latency equal to the stability window.

3. Integrator or shift-register methods: Shift samples into a byte and treat 0xFF as pressed and 0x00 as released. It is elegant and cheap.

The latency trade-off

Here is the catch: debounce time is latency. Gaming mouse makers compete on responsiveness, so firmware may use very short debounce windows. That works fine when switches are new and clean. As contacts wear or oxidise, bounce lasts longer, can exceed the debounce window and gets reported as a second click.

That is the root of the famous "mouse double-click problem". It is not usually a software bug, but an ageing switch outliving its firmware assumptions.

Some manufacturers now let users adjust debounce time in companion software, trading a few milliseconds of latency for reliability. Others moved to optical switches, where a light beam replaces metal contacts and bounce largely disappears.

Observing bounce without an oscilloscope

You can see the symptoms from the operating system side. Browsers expose mousedown/mouseup events with high-resolution timestamps via event.timeStamp. If you log the interval between consecutive presses of the same button, human-made presses rarely come closer than about 50â€“80 ms. Intervals of a few milliseconds suggest bounce leaking through.

A minimal logger:

let last = 0;
addEventListener("mousedown", (e) => {
  const t = e.timeStamp;
  console.log(e.button, (t - last).toFixed(1), "ms");
  last = t;
});

For non-developers, a ready-made double click test does the same thing with a friendlier interface. You press a button 25 times, and it logs each interval, flags unusually short repeats and exports a CSV. It is a useful diagnostic, with the caveat that it measures what the browser observes, after OS and firmware processing, and not the raw electrical signal.

Beyond mice

Bounce affects anything with mechanical contacts:

  • Keyboards: Chattering keys type double letters. Mechanical keyboard firmware such as QMK exposes debounce algorithms and timing.
  • Embedded projects: Every Arduino beginner meets bounce on their first button.
  • Industrial controls: Limit switches and relays need debouncing to avoid false triggers.
  • Rotary encoders: Bounce causes skipped or reversed steps, a classic cause of jumpy scroll wheels.

Takeaways

  1. Physical switches always bounce. The only question is by how much.
  2. Debounce logic trades latency for reliability.
  3. Ageing switches can outgrow their firmware's debounce window.
  4. Optical switches and adjustable debounce are the modern answers.
  5. You can observe the symptoms in a browser in a few lines of JavaScript.

Next time your mouse opens a folder you only meant to select, you will know exactly what is going on: a few microscopic metal contacts, bouncing just a little too long.

The request: Request problem

This is the biggest difference and the reason drogue exists.

slowapi requires you to add request: Request to every decorated endpoint:

# slowapi
from slowapi import Limiter

from starlette.requests import Request

limiter = Limiter(key_func=get_remote_address)

@app.get("/api/data")
@limiter.limit("10/minute")
async def get_data(request: Request):   # rate limiter leaked into your signature
    return {"data": "value"}

Now your business logic is coupled to the rate limiter. Change the limiter,
rewrite every endpoint. Test the endpoint without HTTP, mock the request.

drogue extracts identity from the ASGI context without touching your signature:

# drogue
from drogue.adapters.fastapi import DrogueLimiter

limiter = DrogueLimiter(app)

@app.get("/api/data")
@limiter.limit("10/minute")
async def get_data():                   # clean
    return {"data": "value"}

Algorithm choice matters

slowapi uses Fixed Window only. "30/minute" means exactly 30 requests,
then hard stop. That's fine for strict quotas but harsh on bursty traffic.

drogue defaults to Token Bucket, which allows short bursts above the average
rate. A "30/minute" limit with Token Bucket might briefly allow 35 requests,
then smooth out. For strict quotas, use algorithm=AlgorithmType.FIXED_WINDOW.

The choice between burst-friendly and strict-per-window is a design decision,
not a bug. slowapi just doesn't offer the option.

WebSocket rate limiting

Neither slowapi nor flask-limiter supports WebSocket rate limiting. If you
have real-time features (chat, notifications, games), you need drogue or
roll your own.

#10209. Understanding SQEs and CQEs with kqring on FreeBSD

If you have used an event loop, you have probably written some variation of this:

  1. Wait for a socket to become readable.
  2. Read from it.
  3. Process the bytes.
  4. Go back to waiting.

A completion-based I/O interface moves some of that work across the application/kernel boundary. Instead of asking which sockets might be ready, the application can describe the reads it wants and collect their results later.

kqring is an experimental FreeBSD kernel module that exposes an io_uring-oriented interface using FreeBSD's own kernel facilities. It is a useful example for understanding what submission and completion queues actually do, and why their memory-lifetime rules matter.

Readiness and completion answer different questions

For a network receive, a readiness notification answers:

Can this socket probably be read without waiting?

The application still needs to perform the receive. Another thread might consume the available data first, so the application also needs to handle readiness changing before it acts.

A receive completion answers:

What happened to the receive that was submitted?

That result might be 100 bytes read, an error, or end of file. The operation itself has been attempted or completed according to the interface's contract.

This distinction describes the network paths, not everything kqueue can do. FreeBSD's kqueue also supports other event sources, including asynchronous I/O completion notifications.

An SQE describes work

SQE stands for Submission Queue Entry. It contains the operation and its arguments.

Conceptually, a read request might look like this:

operation: READ
file:      descriptor 7
buffer:    address of a 4096-byte buffer
length:    4096
user_data: 42

A real program also has to set up the ring, publish the entry with the right memory ordering, and tell the kernel about it. A library such as liburing handles that bookkeeping; the real code is below.

The user_data value belongs to the application. It could be an integer identifying a request or a value associated with application state. The kernel returns it with the result so the application can match the completion to the right request.

A CQE reports a result

CQE stands for Completion Queue Entry. Its important fields are:

Field Meaning
user_data The value associated with the submitted request
res The operation's result, such as bytes transferred or a negative error
flags Additional information about the completion

If the example read transfers 100 bytes, a completion could contain:

user_data: 42
res:       100
flags:     0

An error is reported through a negative result. A read that reaches end of file normally reports zero bytes.

The basic exchange is:

Application prepares SQEs
          |
          v
Kernel consumes requests and performs or schedules work
          |
          v
Kernel posts CQEs
          |
          v
Application collects results and updates its own state

Completions need not arrive in submission order. Matching by user_data lets the application manage requests that finish at different times.

The same read in C

Here is that read with liburing, built against kqring's liburing 2.9 port and saved as readone.c. Error handling is trimmed to the essentials:

#include <liburing.h>
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>

int
main(void)
{
    struct io_uring ring;
    struct io_uring_sqe *sqe;
    struct io_uring_cqe *cqe;
    char buf[4096];
    int fd, ret;

    ret = io_uring_queue_init(8, &ring, 0);
    if (ret < 0) {
        fprintf(stderr, "queue_init: %s\n", strerror(-ret));
        return (1);
    }
    fd = open("/etc/hosts", O_RDONLY);
    if (fd < 0) {
        perror("open");
        return (1);
    }

    /* Describe the read: an SQE. */
    sqe = io_uring_get_sqe(&ring);
    io_uring_prep_read(sqe, fd, buf, sizeof(buf), 0);
    io_uring_sqe_set_data64(sqe, 42);
    io_uring_submit(&ring);

    /* Collect its result: a CQE. */
    ret = io_uring_wait_cqe(&ring, &cqe);
    if (ret < 0) {
        fprintf(stderr, "wait_cqe: %s\n", strerror(-ret));
        return (1);
    }
    printf("user_data=%llu res=%d\n",
        (unsigned long long)io_uring_cqe_get_data64(cqe), cqe->res);
    io_uring_cqe_seen(&ring, cqe);

    close(fd);
    io_uring_queue_exit(&ring);
    return (0);
}

cc -O2 -I work/liburing-liburing-2.9/src/include -I freebsd/include \
    -include freebsd/include/config-host.h -o readone readone.c work/out/liburing.a

The source is the same as it would be on Linux. What differs is underneath: liburing's three system calls go to kqring's, and values such as O_RDONLY and the error numbers in res are FreeBSD's.

One request can produce several completions

A multishot request can remain active after producing a result. For example, a multishot receive can produce completions for successive receives without requiring the application to submit an entirely new receive request each time.

IORING_CQE_F_MORE tells the application that the request remains active and can produce more completions. A completion without that flag ends the multishot request.

This changes the application's bookkeeping. It must not discard the request state just because the first CQE arrived. It also needs a buffer strategy appropriate for multiple results, such as provided buffers, and must handle the conditions that terminate the request.

The kernel still needs somewhere to execute the work

A ring is a communication mechanism. It does not make every operation cheap or automatically nonblocking.

kqring uses several execution paths:

  • Ready socket operations can execute during the submitter's entry into the kernel.
  • Sockets that would block wait for a socket callback that queues a retry.
  • Eligible cached file reads and ready pipes can execute inline.
  • Operations that need to wait can run on kernel workers associated with the owning process.
  • Supported disk-device operations can use the native bio path.

The code also uses kqueue internally. Its non-socket polling adapter, called kpoll, registers events for objects such as pipes and eventfds and converts them into completions.

So kpoll and kqueue are not competing choices here. Kpoll is the part of kqring that connects internal kqueue events to the submission/completion model.

Batching can save work

Suppose many sockets already have data available. A readiness loop can collect their events together, but the application still performs the receives. A completion interface can describe those receives in advance and collect their results as a batch.

The benefit depends on the workload. Preparing queue entries, holding references, scheduling workers, and posting results all have costs. One operation per kernel entry may add overhead without enough batching or overlap to recover it.

That is why an evaluation needs more than the fastest benchmark row. Useful questions include:

  • How many operations are submitted together?
  • Is the data already available, or does the request need to wait?
  • Does execution require a worker handoff?
  • How much CPU time and memory does the workload consume?
  • Which event marks the operation as finished for the measurement?

An interface can make one workload cheaper and another more expensive. The project documents both favorable and unfavorable microbenchmark results; they should not be read as a claim that every application becomes faster.

A completion also has an ownership meaning

The buffer address in a request is more than an argument. It is a promise that the memory remains usable for as long as the operation needs it.

Copying the request's metadata does not copy the payload. Once submission has consumed an iovec description, for example, its metadata may be reusable under the interface contract while the described data buffer still has to remain available.

Cancellation adds another distinction. In kqring, a successful asynchronous cancellation result can arrive before the target worker has returned. The target's final completion is the event to wait for before reusing its ordinary I/O buffer. Requesting interruption is not the same as proving the worker has stopped.

Zero-copy sends have a further boundary. The primary send result can arrive while outgoing network buffers still retain references to the application's pages. A later release notification tells the application when it may reuse that transmission memory. Neither notification means that the remote application has processed the data.

For each request, ask: which completion actually ends the resource's lifetime obligation?

Compatibility has limits

kqring follows io_uring structures and operation identifiers, but uses native FreeBSD values for flags such as O_* and MSG_*, and native error numbers in completion results.

Its public header supplies three entry points:

Linux interface Native kqring wrapper
io_uring_setup() kqring_setup()
io_uring_enter() kqring_enter()
io_uring_register() kqring_register()

The repository includes an overlay for liburing 2.9. This can preserve the library-level programming model, but Linux-specific assumptions in an application still need review. This is a native source-porting interface, not a way to execute an unchanged Linux binary.

There are behavioral differences too. Rings belong to one process, and a forked child cannot generally submit work through its parent's ring. Signal-mask handling and exec behavior also differ. A familiar operation name does not remove the need to read those contracts.

Where the implementation stands

The current project documentation identifies FreeBSD 15.1-RELEASE, amd64, with a GENERIC kernel and matching kernel sources as the supported system. Other releases and architectures have not been tested according to that documentation.

The module is an experimental preview and has not had an independent security audit. Functional tests and compatibility tests help check specific behaviors; they do not establish the absence of kernel concurrency or memory-safety bugs.

The source repository contains the implementation, architecture notes, compatibility differences, tests, and benchmark procedure. For the version discussed here, see the project overview at release 0.1.0.

The useful mental model is a request with an explicit lifetime: the SQE describes it, the kernel chooses how it executes, and CQEs report the state transitions the application needs to observe. Understanding those transitions is what makes the interface usable safely.

TabPFN: who's actually coming?

TabPFN is Prior Labs' tabular foundation model, and it suits community data suspiciously well: no training loop, no hyperparameter tuning, strong on small tables of a few thousand rows, and fine with missing values.

Each RSVP becomes a row of 27 features, using only what was known beforehand:

  • RSVP timing: days ahead, place in the sign-up order, guests
  • Attendee history: regular or first-timer, from strictly earlier events
  • Event: series, weekday evening vs Saturday, online vs in-person, waitlist, food
  • PH calendar: holidays, long weekends, the wet season, and payday. Pay lands on the 15th and month-end (kinsenas at katapusan), and the broke days before are petsa de peligro. A free talk still costs fare and dinner.
  • Rain: daily rain at the venue, or your own PAGASA table. Weather data by Open-Meteo.com.

From probabilities to a headcount

TabPFN rates the regular who never misses PyMeets high and the first-timer who RSVP'd three weeks ago low. Summing gives an average, but a pizza order needs the risk too.

So each RSVP is a weighted coin flip with its own odds (weighted, because "+1 guest" is two heads). If the coins were independent, the total would follow a Poisson-binomial distribution, computed exactly rather than simulated. But a downpour or a jammed EDSA moves everyone at once, so the distribution is mixed over a shared event-day shock, sized by how far earlier forecasts missed. That gives the odds of every headcount, and a p10 to p90 range as wide as our history says it should be.

Decisions: plain Python, simple math

The LLM never does math. The planner does, with adjustable defaults:

  • Pizza: order for the 75th percentile of heads, not every RSVP. Boxes = ⌈heads × 3 slices ÷ 8 per box⌉, so a p75 of 40 heads means 15 boxes. Add a box price to see pesos saved.
  • Waitlist: fold waitlisted RSVPs (with their own odds) into the distribution and release as many as keep P(heads > capacity) ≤ 10%.
  • Seats, name tags, e-certificates: the 90th percentile, counting the people just let in.

Why p75 for pizza but p90 for chairs? Leftover pizza costs money. A missing chair costs dignity.

#10212. BiCS FLASH memory controller error correction and data reliability enhancement (ECC) function

High-capacity, high-density flash memory such as BiCS FLASH (3D NAND) is prone to bit inversion due to minute charge loss (retention degradation) and interference between adjacent cells (read disturb), making robust error correction (ECC: Error Correction Code) essential. While this is usually handled by hardware (LDPC or BCH engine), we have created sample code here that simulates a process where the device driver (software layer) controls and monitors the hardware ECC engine, and performs read retries (re-reading by adjusting the read voltage) as needed.

This code complies with the Ministry of Economy, Trade and Industry's IPA's "ESCR [C language version] Ver. 3.0," and thoroughly implements defensive programming, constant definition, and const qualifiers.

1. Sample Code 

#include <stdint.h>
#include <stdbool.h>
#include <stddef.h>

/* Constants Definition (Elimination of Magic Numbers) */
#define BICS_PAGE_DATA_SIZE         (4096U) /* User data size (4KB) */
#define BICS_PAGE_PARITY_SIZE       (256U)  /* Parity data size */
#define BICS_MAX_CORRECTABLE_BITS   (120U)  /* Maximum correctable bits (Assuming LDPC) */
#define BICS_MAX_READ_RETRY_COUNT   (5U)    /* Maximum limit for read retry (voltage shift) */

/* ECC Operation Result Codes */
typedef enum {
    BICS_ECC_SUCCESS = 0,         /* No errors (or parity generation successful) */
    BICS_ECC_CORRECTED = 1,       /* Errors successfully corrected */
    BICS_ECC_UNCORRECTABLE = 2,   /* Uncorrectable errors (e.g., retry limit exceeded) */
    BICS_ECC_INVALID_PARAM = 3    /* Invalid parameters provided */
} bics_ecc_result_t;

/* Mock Interface for Hardware ECC Engine */
typedef struct {
    /* Reads data/parity and returns the number of error bits using Hard Decision */
    uint32_t (*hw_decode_hard)(const uint8_t* data, const uint8_t* parity);
    /* Shifts the read reference voltage (Vth) for Read Retry */
    bool (*hw_shift_read_voltage)(uint8_t retry_step);
    /* Reads the raw page data from NAND flash again */
    bool (*hw_read_page_raw)(uint32_t block, uint32_t page, uint8_t* data, uint8_t* parity);
} bics_ecc_hw_engine_t;

/* ECC Management Context */
typedef struct {
    bics_ecc_hw_engine_t hw_engine;
} bics_ecc_context_t;

/**
 * @brief  Generates parity data during a write operation (Encoding)
 * @note   ESCR Compliant: NULL pointer checks, const correctness applied
 */
bics_ecc_result_t bics_ecc_encode(
    const bics_ecc_context_t* const ctx,
    const uint8_t* const data,
    uint8_t* const parity_out) 
{
    if ((ctx == NULL) || (data == NULL) || (parity_out == NULL)) {
        return BICS_ECC_INVALID_PARAM;
    }

    /* In a real scenario, this transfers data to the hardware to generate parity. */
    /* For simulation purposes, we initialize the parity buffer to 0. */
    for (uint32_t i = 0U; i < BICS_PAGE_PARITY_SIZE; i++) {
        parity_out[i] = 0x00U;
    }

    return BICS_ECC_SUCCESS;
}

/**
 * @brief  Performs error correction (Decoding) and Read Retry on read operations
 * @note   ESCR Compliant: Comprehensive error handling, clear loop boundaries
 */
bics_ecc_result_t bics_ecc_decode_with_retry(
    const bics_ecc_context_t* const ctx,
    uint32_t block,
    uint32_t page,
    uint8_t* const data,
    uint8_t* const parity) 
{
    if ((ctx == NULL) || (data == NULL) || (parity == NULL)) {
        return BICS_ECC_INVALID_PARAM;
    }
    if ((ctx->hw_engine.hw_decode_hard == NULL) || 
        (ctx->hw_engine.hw_shift_read_voltage == NULL) || 
        (ctx->hw_engine.hw_read_page_raw == NULL)) {
        return BICS_ECC_INVALID_PARAM;
    }

    uint8_t retry_count = 0U;
    uint32_t error_bits = 0U;

    while (retry_count <= BICS_MAX_READ_RETRY_COUNT) {
        /* Execute error detection and correction via Hardware ECC Engine */
        error_bits = ctx->hw_engine.hw_decode_hard(data, parity);

        if (error_bits == 0U) {
            return BICS_ECC_SUCCESS; /* No errors found */
        }
        if (error_bits <= BICS_MAX_CORRECTABLE_BITS) {
            return BICS_ECC_CORRECTED; /* Errors were correctable */
        }

        /* If uncorrectable, perform a Read Retry by adjusting the read voltage */
        retry_count++;
        if (retry_count <= BICS_MAX_READ_RETRY_COUNT) {
            if (!ctx->hw_engine.hw_shift_read_voltage(retry_count)) {
                return BICS_ECC_UNCORRECTABLE; /* Voltage shift operation failed */
            }
            if (!ctx->hw_engine.hw_read_page_raw(block, page, data, parity)) {
                return BICS_ECC_UNCORRECTABLE; /* Raw read operation failed */
            }
        }
    }

    /* Uncorrectable ECC error (UECC) occurs if correction fails after maximum retries */
    return BICS_ECC_UNCORRECTABLE;
}

Key Points of ESCR Ver.3.0 Compliance

  1. Ensuring NULL Safety (M101 / M102, etc.): Strict NULL checks for structure pointers and hardware operation function pointers are performed at the beginning of functions in bics_ecc_encode and bics_ecc_decode_with_retry.

  2. Strict Const Modifier Use (M113): The const modifier is applied to argument pointers that cannot be changed (context, read-only data). This prevents unexpected data corruption (such as buffer overflows) at the compilation stage.

  3. Elimination of Magic Numbers (M122): Page size, maximum number of retries, and allowable error bits are all defined using #define (or enum), and constants are given the U suffix to indicate they are unsigned.

  4. Use of fixed-length integer types (M203): Instead of using environment-dependent types such as int, we have standardized to uint32_t and uint8_t from , eliminating embedded-specific data size issues.
