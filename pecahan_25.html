#27991. I Built an Offline AI That Organizes My Downloads So I Don't Have To

This is a submission for the Hacktoberfest Open-Source AI Challenge Week 3: Slow and Steady.

We've all been there. You download an assignment, a certificate, a PDF, a screenshot, or an invoice, thinking you'll organize it later.

But later rarely comes.

Before you know it, your Downloads folder is filled with files named document(3).pdf, final_final_v2.docx, and IMG_20261023.png. Finding something important becomes a task of its own.

For this week's Slow and Steady challenge, I wanted to build something that rewards doing absolutely nothing.

So I built HushFile, a fully offline, open-source AI file organizer that quietly handles your digital clutter in the background.

The idea is simple: Drop it in Downloads, forget it, find it later.

What I Built

HushFile is an autonomous desktop background agent that watches your Downloads folder, understands incoming files using locally running AI models, gives them meaningful names, and moves them into appropriate folders.

Unlike traditional file organizers that depend mainly on extensions or manually configured rules, HushFile analyzes the contents of supported files to determine what they actually contain.

For example, a randomly named PDF containing an educational certificate can be recognized and organized under Education instead of being treated as just another PDF.

And because AI isn't always right, HushFile is designed with safety mechanisms that let users review and reverse its decisions.

What makes HushFile useful?

1. Automatic file organization

HushFile monitors the Downloads folder using a background watcher. When a new file arrives, it waits until the download is complete before processing it.

It then extracts relevant content, determines the document type, generates a descriptive filename, and moves the file into its appropriate category.

2. Understanding multiple file formats

HushFile isn't limited to text documents. Its extraction pipeline supports:

  • PDFs, including scanned documents using OCR
  • Word documents, spreadsheets, and CSV files
  • Images and screenshots
  • Audio recordings and voice notes
  • Text files and source code

Different extraction tools handle different formats, while local AI models interpret the extracted information.

3. Crash-safe undo

This was one of my biggest priorities.

Allowing an AI to move personal files automatically introduces a serious concern: what happens when it makes a mistake?

HushFile maintains a SQLite-based undo journal that records file operations. Users can reverse individual moves or entire batches.

It also checks file hashes before restoration and avoids overwriting an existing file when restoring to an occupied location.

The goal is to make automation convenient without making it careless.

4. Search files by meaning, not just filename

Sometimes we remember what a document contains but not what it was called.

HushFile uses local text embeddings and a vector database to support semantic search.

Instead of remembering an exact filename, I can search for something like:

cloud server invoice from last quarter

The system can retrieve relevant indexed files using their content and metadata.

5. Quick-Info cards

HushFile provides a Quick-Info feature that explains how a file was understood and organized.

It can show the detected document type, summary, relevant facts, tags, category, and classification details.

This helps make the AI's decisions more understandable instead of leaving users wondering why a file ended up in a particular folder.

6. Daily activity digest

Rather than manually checking every folder, users can review what HushFile processed, including organized files, duplicates, items requiring review, and failures.

It's a small feature, but it captures the idea behind this week's theme: let the software do the routine work, and check the results when you want to.

Demo

HushFile is designed to run locally on a desktop or laptop, so there is no hosted cloud demo.

A typical demonstration includes downloading a document, letting HushFile detect and organize it, reviewing the explanation behind the decision, searching for it using natural language, and undoing the move.

The CLI also supports a dry-run mode, allowing users to preview proposed changes without modifying files.

Local demo commands:

hushfile doctor
hushfile scan --dry-run
hushfile start
hushfile recent
hushfile find "cloud server invoice"
hushfile undo
hushfile ui

The full setup instructions are available in the GitHub repository.

Code

The complete project is publicly available on GitHub.

It is built primarily with Python and is designed for local execution on Windows, Linux, and macOS.

Anyone interested in local AI, privacy-conscious automation, or file management can explore the implementation and adapt it to their needs.

How I Built It

I built HushFile around one important decision:

The open-weight AI model should run on the user's own computer, not behind an external inference API.

The processing pipeline

When a new file enters the monitored folder, HushFile follows a structured workflow:

Detect → Stabilize → Fingerprint → Extract → Understand → Decide → Organize → Index

First, the folder watcher detects a new file and checks that it has finished downloading.

Next, SHA-256 fingerprinting helps identify duplicate content.

Depending on the file format, HushFile extracts text, performs OCR, or uses audio transcription or vision processing.

The extracted information is then passed to a local language model, which generates a structured result containing the proposed category, filename, summary, and metadata.

Pydantic validates the model output before the decision engine uses it.

If the model output is invalid, the pipeline includes a retry and a deterministic fallback. Low-confidence results can be routed to a review folder rather than being blindly organized.

Finally, the move is recorded in the undo journal, and file information is indexed for subsequent searches.

Designing for limited hardware

Another challenge was making the pipeline practical on consumer hardware.

The project targets laptops with approximately 8 GB of GPU VRAM rather than requiring an expensive dedicated AI server.

Running several language, vision, and audio models simultaneously can exhaust available memory.

To address that, HushFile uses a sequential processing queue and Ollama model lifecycle controls so that large models don't need to remain loaded simultaneously.

The trade-off is throughput: files are handled sequentially, so large batches can take time.

But for an assistant that quietly processes downloads in the background, predictable memory consumption matters more than processing everything at once.

How I approached safety

Autonomous file operations need more than a good classification model.

HushFile includes safeguards such as:

  • Write-ahead journal records for file operations
  • Checksum verification for undo
  • Filename collision handling
  • Dry-run previews
  • Review routing for uncertain classifications
  • Deterministic fallbacks when model output is invalid
  • Treating document content as untrusted input

The goal wasn't simply to make an AI that organizes files. It was to make one whose actions could be inspected and reversed.

Model evaluation

I also wanted to evaluate the models rather than assume that a larger model would automatically be better.

The repository includes benchmark tooling for comparing category accuracy, average processing time, review routing, and peak GPU memory use.

The README reports the following results on its labeled test set:

Model Category accuracy Average time/file Review share Peak VRAM
Qwen3 4B (CUDA) 100% 45.2 seconds 15% 3,741 MB
Rule-based fallback (CPU) 60% 3.7 seconds 80% 0 MB

These are project-specific results, not claims of general document-classification accuracy.

The comparison shows an important trade-off: the local language model provides more capable classification on this dataset, while the rule-based fallback processes files much faster with minimal hardware requirements.

This also highlights why the review queue matters. An autonomous organizer should have a way to handle uncertain cases instead of forcing every file into a possibly incorrect category.

Why Does Open Innovation Matter?

For HushFile, open innovation isn't just about making the source code public.

It's what makes the entire approach practical.

1. Personal documents can stay personal

Our Downloads folders can contain some of our most sensitive information: identity documents, certificates, invoices, financial statements, and personal records.

With a cloud-based AI workflow, file contents may need to be transmitted to a third-party service for processing.

HushFile instead uses local inference. After the necessary software and models have been downloaded, its core AI processing can operate without an internet connection.

The application does not require users to upload personal files to an external model API.

2. No per-document inference API fees

A cloud-based AI workflow can introduce usage-based inference costs.

With HushFile, the model runs locally. Processing additional documents doesn't generate per-file charges from an external inference provider.

Of course, local inference still consumes electricity, disk space, CPU/GPU resources, and time. It isn't literally free.

But users gain much more control over their operating costs.

3. Models are replaceable

The project isn't permanently tied to one model provider.

Ollama makes it possible to experiment with different compatible open-weight models, allowing users to evaluate trade-offs between speed, memory usage, and classification quality.

That matters for hardware accessibility. A configuration suitable for a gaming laptop might not be ideal for a smaller CPU-only machine.

4. The system is inspectable and customizable

Developers can inspect the pipeline, change classification categories, modify naming conventions, evaluate model performance, or extend supported file formats.

The underlying behavior is not hidden behind an inaccessible service.

5. Local AI has limitations too

Running models locally introduces installation complexity, hardware constraints, and slower inference on less powerful machines.

An AI classifier can still misunderstand documents or produce inaccurate metadata, even when its output follows a valid schema.

That's why HushFile combines AI interpretation with conventional software safeguards, fallback rules, human review, and undo functionality.

For this project, the biggest benefit of open innovation is control: control over where data goes, which models run, how files are handled, and how mistakes are corrected.

The Lazy Payoff

The best part of HushFile is that its intended daily workflow barely involves the user.

Instead of repeatedly opening Downloads, reading filenames, creating folders, renaming files, and deciding where everything belongs, I can delegate those repetitive steps to a local background process.

And when I need something later, semantic search reduces my dependence on remembering exact filenames.

I don't have a verified daily time-savings figure yet, so I won't claim HushFile saves a specific number of minutes per day.

What I can measure is the work the software is designed to replace: repetitive classification, naming, moving, and searching.

The current model benchmark also makes an important point: local AI processing isn't necessarily instantaneous. In the reported run, Qwen3 4B averaged 45.2 seconds per file.

But the philosophy of Slow and Steady isn't that every operation must be fast.

It's that the computer can handle the boring work at its own pace while I focus on something more useful.

And that is exactly what I wanted HushFile to do.

Final Thoughts

This project taught me that useful AI automation isn't only about making a model perform a task.

It's also about making the surrounding system reliable, explainable, private, and recoverable when things go wrong.

HushFile isn't the first AI-powered file organizer, and there are already open-source projects exploring local document classification and file organization.

My focus was on combining that capability with a crash-safe undo journal, explainable file information, semantic retrieval, and reproducible local-model benchmarks.

There's still room to improve, particularly in learning from user corrections, expanding the evaluation dataset, and supporting more languages.

But the central idea is already clear:

Not every AI assistant needs to live in the cloud, and not every useful automation needs constant supervision.

Sometimes, the most useful assistant is the one that quietly handles the boring work and lets you get on with your day.

Drop it in Downloads. Forget it. Find it later.

#27992. Meta's Crawler Goes Live Oct 30. Your Real Deadline Is Oct 29.

Five days left until Meta's crawl clause kicks in.

Actually — four. And if you're planning to touch your robots.txt on the morning of October 30th, you've already missed it.

Here's the detail that changes the calendar: Meta's own crawler documentation says a robots.txt change can take up to 24 hours to apply. I flagged this in passing in the original Oct 30 checklist, and it's been sitting in my head ever since, because it quietly moves the real deadline a full day earlier. The clause goes live on the 30th. Your last safe edit is the 29th — and that's if propagation behaves. Prudent version: treat the 28th as your deadline and spend the 29th verifying.

Quick recap so this stands on its own: Meta's updated Commercial Terms say that from October 30, 2026, using Meta's products for business — ads, a Page, a catalog, WhatsApp Business — authorizes Meta to crawl the websites "associated with" that account and use what it collects to train its products. No opt-out short of stopping business use entirely. The original piece walks the clause itself, Meta's pushback, and the per-bot decisions. This one is narrower: how to verify, in the last few days, that what you decided is what crawlers will actually get.

Because deciding and getting are two different things. That gap is where most sites are about to get surprised.

The three mismatches your audit will probably find

1. The file you edited isn't the file being served. Staging and production drift. Repos and live servers drift. CDNs cache robots.txt like any other file, and an old cached copy can outlive your deploy by hours. The only robots.txt that matters is the one a crawler fetches from your public domain today — not the one in your repo, not the one you remember writing.

2. Your server quietly disagrees with your robots.txt. This one has data behind it: a study of the top 1,000 sites found 8–11% server-refuse AI crawlers their robots.txt explicitly allows — a bot-management rule or firewall closing a door the owner wanted open. robots.txt states your policy. Your logs show your reality. Related trap: Cloudflare retired its one-click "Block AI Bots" toggle in September, and one analysis found 118 sites silently lost their GPTBot bans around the change. Set-and-forget bot rules have a habit of forgetting themselves.

3. Your rules were copy-pasted from a gist written for a different internet. The most common version: a "block AI training" snippet from before the answer-crawler distinction existed, which blocks user-initiated fetching along with training. Block ChatGPT-User and "summarize this URL" breaks for every ChatGPT user who shares your link — while you stare at a traffic dip you can't explain. This came straight out of the comments on the original piece (credit to alexcodebytes, who'd watched it happen repeatedly), and it's why I turned the per-bot breakdown into its own thing: GPTBot vs OAI-SearchBot vs ChatGPT-User: what to block (and keep). Short version: decide per purpose — training versus answers — never per company logo.

The 10-minute verification protocol

Run this once this week, and again on the 29th:

  1. Fetch your robots.txt like a crawler does. curl -s https://yoursite.com/robots.txt — from outside your network if you can. Diff it against the copy in your repo. Any difference is a bug, full stop.
  2. Check whether the CDN is serving a cached copy. curl -sI https://yoursite.com/robots.txt and look at the cache headers. If it says HIT with an age older than your last edit, purge it and re-fetch.
  3. Probe with the crawler's user-agent. curl -s -o /dev/null -w "%{http_code}" -A "meta-externalagent" https://yoursite.com/ — this won't replicate Meta's full behaviour, but WAF and bot rules keyed on user-agent strings will show themselves here. A 403 on a bot you meant to allow is exactly the mismatch from the study above.
  4. Take a log baseline now. grep -i "meta-externalagent" access.log | tail -20 — whatever this week looks like is your "before" picture. Without it, you'll have no idea whether October 30 changed anything.
  5. Re-check the rest of the stack. CDN bot-management page, WAF rules, any "block AI bots" toggle you set months ago. Confirm each one still says what you think it says — then confirm the served file (step 1) agrees with it.

If robots.txt turns out not to be enforcement enough for your situation, the heavier layers are compared here: 5 ways to block AI crawlers — what actually works. Robots.txt is the polite layer. Know which layer you're actually relying on.

After October 30: what to watch

Nothing explodes on the 30th. What changes is that the crawl becomes contractual business-as-usual, so your logs become the story:

  • Watch for meta-externalagent in the first week's logs. Volume, which sections it touches, whether it respects the lines you drew. Compare against this week's baseline.
  • Keep meta-webindexer and facebookexternalhit mentally separate. One feeds Meta AI citations, the other renders your link previews. Seeing "Meta" in a log line is not one event — it's three different products with three different consequences, and only one of them is the training crawler this whole debate is about.
  • Put a monthly re-check on the calendar. Vendors rename bots, retire toggles, and rewrite docs. The 44.5% stat from the GeoParrot census — sites blocking GPTBot that also blocked the search bot by accident — wasn't malice or stupidity. It was drift. Your file will drift too.

What I'd actually do

If I ran a content site with a Facebook Page, this week looks like: per-purpose rules written explicitly (training crawlers disallowed, answer crawlers open), the protocol above run twice, a log baseline saved somewhere I won't delete, and then — honestly — I'd stop thinking about it until the November re-check. The clause is a contract story more than a crawler story; the crawler hygiene is a one-evening job if your stack cooperates, and the verification matters more than the rules themselves. Everyone writes rules. Almost nobody fetches their own robots.txt to see what the internet thinks they wrote.

So here's my question, and I mean it literally: when you fetch your live robots.txt this week — not the repo copy, the served one — is it the file you think it is? If your audit found one of the three mismatches, which one? I suspect mismatch #1 is quietly everywhere, and I'd love the data either way.

The check floor is −0.3 V. Added-capacitor and snubber proposals did not fix it, so they were not adopted into the board. #27994. I'm Too Lazy to Write Alt Text, So Gemma Does It For Me

This is a submission for the Hacktoberfest Open-Source AI Challenge Week 3: Slow and Steady

What I Built

Every codebase I've touched has the same line in it:

<img src="/imgs/cookie.png" alt="" />

It's rarely because we don't care about accessibility. Describing forty images is just the most boring job in front-end, so it gets pushed to "later."

So I built a VS Code extension that does it for me. Hover over any <img> with a missing or empty alt, click Generate alt text, and the description is written straight into your code.

Feeling really lazy? Press Cmd+Shift+A (Ctrl+Shift+A on Windows/Linux) and it fills in every empty alt in the file at once.

A few small rules keep it safe to trust:

  • It never overwrites alt text you already wrote.
  • Failures are reported per image, and the successful ones are still applied.
  • Output is escaped, so a stray quote can't break your markup.

AI Image Alt Text

Generate accessible image alt text in HTML, JSX, and TSX files using a locally running Ollama vision model. Image contents are sent only to the Ollama server you configure.

Features

  • Hover over an <img> element with an empty or missing alt attribute and select Generate alt text.
  • Press Cmd+Shift+A (or Ctrl+Shift+A on Windows/Linux) to fill empty or missing alt attributes in the current file.
  • Supports multiline tags, other attributes, workspace-relative image files, and HTTP(S) image URLs.
  • Existing non-empty alt text is never overwritten. Bulk generation reports individual image failures and applies successful results together.

Requirements

  • Ollama running locally or at a server you can access.

  • A vision-capable model installed in Ollama, for example:

How I Built It

The whole thing runs on Gemma 3 through Ollama, entirely on my own machine.

When you click the button, the extension:

  1. Finds the image. It checks the workspace root first, then common static folders like public/, so /imgs/cookie.png just works. Remote URLs work too.
  2. Sends it to the local Gemma model with a short prompt asking for a concise, useful description.
  3. Writes the result back into the alt attribute.

Setup is two steps: ollama pull gemma3:latest, then point the extension at your Ollama URL. The model name is a setting, so you can swap in any other vision model without touching the code.

Why Does Open Innovation Matter?

Alt text feels like a perfect job for a hosted API, until you think about what you'd be sending it.

Your images stay yours. Client mockups, unreleased products and internal dashboards often sit in a repo long before anyone should see them. With a local model, nothing leaves the laptop.

It costs nothing per image. A big project can have hundreds of images. Running them through Gemma costs electricity, not a bill that grows with your codebase.

It's swappable. If a better open vision model shows up next month, it's a one-line settings change. I'm not tied to one provider's pricing or availability.

The honest trade-off: a local model is slower than a hosted API. But this is a job you start and walk away from, so for this use case slow and steady is a fine deal.

The Lazy Payoff

I ran it on 20 images from one of my projects.

  • Time: just 3 minutes, versus roughly 10 minutes writing them by hand.
  • Usable as-is: 18 out of 20 descriptions needed no editing.
  • Where it struggled: Animated or vector images eg gif files

#27997. EU Chatbot Runtime Selection: Making Linguistic Nuance Auditable Per Tenant

EU Chatbot Runtime Selection: Making Linguistic Nuance Auditable Per Tenant

A runtime choice for an EU chatbot should be made from two ledgers: one for language behavior and one for tenant-level spend. For a gaming company that turns sales calls into CRM actions, I would keep the model behind a small, replaceable runtime boundary, record usage per tenant and locale, and promote a runtime only after it passes an intent-and-action test set.

TL;DR

Linguistic nuance is not a model name. It is a measurable combination of locale handling, register, ambiguity resolution, and safe action selection. Start with real call excerpts labeled by language, dialect, intent, and allowed CRM action. Run the same set through candidate runtimes, retain the raw outputs, and attach every request to a tenant, locale, and cost record. Choose the option whose errors are explainable and whose spend can be reconciled, not the option with the most impressive demo.

The application in this example is deliberately concrete. A gaming publisher receives sales calls from European partners. The chatbot summarizes a call, extracts follow-up actions, and proposes structured CRM updates. A fluent sentence is not enough. “We can probably launch in autumn” should not become a committed launch date, and a polite refusal should not become a positive buying signal.

How should I choose a runtime for better linguistic nuance in an EU chatbot?

The first trap is treating language quality as one score. European conversations can move between English, French, German, Spanish, Italian, and regional forms in the same account. Formality changes the meaning of a request. So does a hedge, a quoted phrase, or a sentence whose subject is omitted.

I would label each evaluation item with four fields: source locale, intended meaning, permitted action, and unacceptable interpretation. Include short utterances, noisy transcript fragments, and code-switched examples. A useful set is small enough for every release to run, but varied enough to expose the edge cases that a polished demo hides.

For the gaming workflow, the permitted actions might be create_follow_up, set_next_contact_date, and add_partner_note. The model can suggest an action, but the application owns authorization and validation. A summary may be prose; an action must be typed data with a tenant identifier, a confidence or review state, and provenance pointing back to the transcript span.

This distinction matters in multilingual text. A runtime can produce a natural translation while losing uncertainty. It can also preserve the words while assigning the wrong business intent. Measure both.

The trade-off is real. A smaller or self-hosted runtime can give tighter control over retention and routing, but may need more locale-specific evaluation and may struggle with long, noisy transcripts. A managed runtime can reduce operational work, but its usage fields, fallback behavior, and data controls may fit your ledger poorly. The right answer depends on which failure the team can actually inspect.

Which runtime boundary keeps the decision reversible?

Put a narrow interface between the CRM workflow and the inference provider. The interface should accept a normalized conversation, locale metadata, a task name, and a tenant context. It should return a typed result plus usage metadata and an error category. The rest of the application should not know provider-specific request shapes.

Here is the shape I use for a testable adapter. The endpoint is intentionally abstract; the important part is the contract and the accounting hook.

from dataclasses import dataclass
from typing import Any, Protocol


@dataclass
class RuntimeResult:
    output: dict[str, Any]
    input_units: int
    output_units: int
    runtime_id: str


class ChatRuntime(Protocol):
    def run(
        self,
        *,
        tenant_id: str,
        locale: str,
        task: str,
        transcript: str,
        schema: dict[str, Any],
    ) -> RuntimeResult:
        ...


def summarize_call(
    runtime: ChatRuntime,
    tenant_id: str,
    locale: str,
    transcript: str,
    action_schema: dict[str, Any],
) -> RuntimeResult:
    result = runtime.run(
        tenant_id=tenant_id,
        locale=locale,
        task="sales_call_to_crm_actions",
        transcript=transcript,
        schema=action_schema,
    )
    record_usage(
        tenant_id=tenant_id,
        locale=locale,
        runtime_id=result.runtime_id,
        input_units=result.input_units,
        output_units=result.output_units,
    )
    return result

The accounting call is part of the application transaction, not a dashboard-only afterthought. Persist a request ID, tenant, locale, task, runtime identifier, input and output units, retry count, and final disposition. If a provider reports usage differently, normalize it at the adapter. Never infer cost from character count after the fact; keep the raw usage fields and the rate-card version used for internal allocation. That extra recordkeeping is slower to implement than a single aggregate counter, yet without it the team cannot tell whether a locale, retry policy, or transcript length caused the bill.

Small detail. Big consequences.

I learned to keep retries visible. A retry that succeeds is still work charged to a tenant, and a fallback can change both language behavior and spend. Hiding either makes the monthly review pleasant and the incident review useless.

How should the evaluation expose ambiguity before production?

Use two gates. The first checks language fidelity: named entities, dates, negation, modality, and the relationship between speakers. The second checks action safety: schema validity, allowed action types, tenant isolation, and human-review routing. A candidate that wins the first gate but invents a date fails the workflow.

Run the set by locale and by tenant segment. Aggregate scores can conceal a weak result in a smaller language group or an expensive long-context tenant. Keep a confusion table for the decisions that matter: positive versus tentative interest, requested versus promised delivery, and “send later” versus “do not send.” These are business distinctions, not literary preferences.

Function calling is useful here because it gives the application a structured boundary for proposed operations, but the application still has to validate arguments and enforce permissions. The runtime must not receive an unrestricted instruction to mutate CRM state. It should propose; a deterministic service should decide whether the proposal is admissible.

A practical release record contains the evaluation dataset version, prompt or instruction version, runtime identifier, locale breakdown, invalid-action count, review rate, retry rate, and tenant-level usage distribution. Keep the examples that failed, including the transcript span and expected interpretation. That history is more valuable than a single headline score.

What should the cost ledger show for each tenant?

Per-tenant cost visibility needs more than a total invoice. At minimum, report requested units, output units, retries, fallback calls, transcript length bands, and the task that caused the work. Separate interactive latency work from batch summarization. Otherwise a heavy batch account can make the chatbot look expensive, or a small number of long calls can disappear inside an average.

The ledger should also show language and runtime dimensions. If German transcripts produce longer outputs than English ones, that is an engineering observation worth testing, not a reason to penalize a locale. If a fallback is used more often for one language, investigate the trigger and the resulting action quality before changing the model.

Do not put a mutable price inside the application’s business logic. Store usage as facts and apply a versioned internal allocation rule during reporting. This keeps historical comparisons stable when external terms change, and it lets finance reconcile the tenant view with the platform view.

A compact event might look like this:

usage_event = {
    "request_id": "req_8f2c",
    "tenant_id": "partner_17",
    "locale": "fr-FR",
    "task": "sales_call_to_crm_actions",
    "runtime_id": "candidate_b",
    "input_units": 1840,
    "output_units": 312,
    "retry_count": 1,
    "review_required": True,
    "rate_card_version": "2026-04",
}

The identifier above is illustrative, but the fields are the important part. Do not log the full transcript into a cost table. Keep sensitive content under the retention and access policy for the conversation system, and link by request ID. A cost audit should not become a second transcript store.

What is a sensible rollout for a replaceable runtime?

Start in shadow mode with a fixed slice of calls and no CRM writes. Compare summaries and proposed actions against the labeled set and human review. Then allow only one low-risk action, such as adding a note that requires approval, while date changes and outbound messages remain gated. Expand by tenant and locale when the error categories are understood.

The migration unit is the adapter plus its evaluation record, not a sweeping rewrite. Version the contract, keep a rollback target, and make the selected runtime observable in every result. A runtime switch that cannot be explained per tenant is not operationally reversible, even if the code change is one line.

The final decision rule is plain: select the runtime that meets the language and action thresholds, exposes enough usage data to allocate work per tenant, and fails in a way the team can review. Linguistic nuance becomes useful when it survives the whole path from transcript to permitted CRM action.

#27998. How Android VpnService Builds a Tunnel, and How TrumanDash Implements It

TrumanDash (楚门快跑) is a free Android VPN from Dockerpay LLC. The package is com.trumandash.android. The product page is trumandash.com. The install target is TrumanDash on Google Play.

VpnService does not encrypt packets. It creates a TUN interface and a routing decision. Encryption, AES-256, and network protocol obfuscation live in the process that reads that TUN. This post separates those layers, then scores TrumanDash against five checks that do not depend on store adjectives.

How does Android VpnService create a network tunnel?

The sequence is fixed by the platform.

  1. VpnService.prepare() returns a consent Intent if this app is not already the approved VPN.
  2. The user accepts the system dialog. That dialog is the whole authorization. It is not an in-app account form.
  3. The service starts, and VpnService.Builder.establish() returns a ParcelFileDescriptor for the TUN device, or null if consent is missing.
  4. The app reads IP packets from that descriptor and writes them to its own encrypted session.
  5. protect(socket) on the session socket keeps that socket on the physical network. Without it, the VPN's own packets re-enter the TUN and the route loops.

A minimal builder, enough to see the contract and not enough to ship:

class TunnelService : VpnService() {
    fun openTun(): ParcelFileDescriptor? {
        return Builder()
            .setSession("TrumanDash")
            .addAddress("10.8.0.2", 32)
            .addRoute("0.0.0.0", 0)          // IPv4 default route
            .addDnsServer("1.1.1.1")
            .setMtu(1280)
            .establish()                       // null if prepare() was skipped
    }
}

What that snippet does not do:

  • It does not add an IPv6 address or ::/0. IPv6 then leaves on the underlying network. That is an IPv6 leak, not a detail.
  • It does not call protect() on the outbound socket.
  • It does not encrypt. A process that reads the TUN and writes plaintext to a socket is a tap, not a VPN.
  • It does not set a blocking mode, a meter flag, or Android's lockdown ("Block connections without VPN"). Lockdown is a user setting on top of an always-on VPN. It is not implied by establish().

AES-256 applies to the session after the packet leaves the TUN, inside the VPN process. Obfuscation is a transform on the outer bytes of that session so a middlebox does not classify the flow by a classic VPN handshake. Neither one is a Builder method.

Official contract: VpnService.

#27999. Exporting HTML Presentations to PPTX in the Browser: Notes for Front-End Developers

Front-end developers often end up as the unofficial "slides person" on a team. We can build a beautiful deck with HTML and CSS in an hour, but the request that follows is almost always the same: "Please send it as PowerPoint." These are my notes on handling that request efficiently, from the perspective of someone who cares about clean markup.

Background: why HTML decks keep appearing

Three trends push presentations toward HTML:

  1. AI generation. Large language models output HTML and CSS reliably. Ask for slides and you get a single .html file.
  2. Frameworks. Reveal.js, Slidev, Marp and similar tools let developers write slides in Markdown and render them as web pages.
  3. Design systems. Teams want slides to match the product's own components, colours and typography.

All three produce web pages, not PowerPoint files.

The core technical mismatch

PowerPoint's OOXML format positions elements absolutely on a fixed canvas. Browsers lay out content with flow, flexbox, grid and fonts that load asynchronously. Translating between the two perfectly is extremely hard. Any practical tool chooses one of two strategies:

  • Render and capture. Render each slide in the browser and place the result in a PPTX slide. This gives a high-fidelity look, but the slides are static.
  • Parse and rebuild. Map DOM elements to PowerPoint shapes. Text remains editable, but complex CSS often breaks.

Knowing which strategy a tool uses tells you what to expect.

A browser-only approach

For my day-to-day use, I prefer a tool that works entirely in the browser, so internal decks are never uploaded to a server. SlideBeaver follows the render-and-capture approach: you open the HTML file, check each slide in a preview, adjust text and spacing in a visual editor, then download a static PPTX.

The output is ideal for presenting, sharing and archiving. It does not produce native, editable PowerPoint text boxes, and it does not embed web fonts. If your stakeholders need to rewrite content inside PowerPoint, generate the deck with a library like PptxGenJS instead.

Preparing markup for conversion

Here are the rules I follow, whatever tool I use:

.slide {
  width: 1280px;
  height: 720px;
  overflow: hidden;
  position: relative;
}
body { margin: 0; }
  • One <section> per slide. Do not depend on JavaScript pagination.
  • System fonts for body text. Fonts from external CDNs may be unavailable or late.
  • Avoid viewport units for slide size.
  • Inline SVG for charts. Canvas-based charts capture one frame only.
  • Relative image paths with assets kept together.

Debugging checklist

Symptom Likely cause Fix
Text shifts or wraps differently Web font not loaded Self-host the font, or wait for document.fonts.ready
Content cut off Slide taller than 720 px Reduce content, or split the slide
Blank image Broken relative path Keep the asset folder next to the HTML
Missing chart Canvas rendered after capture Use SVG, or a static image
Odd colours Blend modes and filters Simplify the CSS

Prompting AI for better input

When asking an assistant to generate slides, include constraints in the prompt:

Output a 16:9 HTML deck. Each slide is <section class="slide">, fixed at 1280×720 px. Use a system font stack. Charts must be inline SVG. Content must be visible without JavaScript.

This removes most conversion problems before they happen.

Version control and iteration

Keep the HTML in Git as the single source of truth. Treat the PPTX as a build artefact: regenerate it whenever the HTML changes, and name it with a date or commit hash. This avoids the classic situation where someone edits the PowerPoint copy and the changes never make it back.

#28000. Routing Browser-Agent Workflows vs. Human SDR Handoffs: The New Speed-to-Lead Frontier

Speed-to-lead has long been a numbers game. The most-cited research is the MIT/InsideSales.com Lead Response Management Study, led by Dr. James Oldroyd. It analyzed more than 15,000 leads and 100,000 call attempts, and found that contacting a lead within five minutes made a team about 100 times more likely to reach that lead, and 21 times more likely to qualify it, than waiting 30 minutes. That study dates from 2007, and its figures are usually repeated through vendor summaries. Treat them as directional evidence of how fast intent decays, not as a precise forecast for your funnel.

Most teams still miss the five-minute window. A 2026 benchmark of B2B inbound leads, reported by Aloware, found a median first response of about 42 hours, with only about 7% of teams responding within five minutes. That gap is the opportunity.

Browser-based AI agents are the newest tool for closing it. They can open a prospect’s website, read a gated page, or work through a portal that has no API, then hand a sales development representative (SDR) a prepared briefing. They also fail in predictable ways, such as CAPTCHAs, login challenges, ambiguous interfaces and high-stakes actions. The workable design is a hybrid. Agents handle research and enrichment, and a well-built escalation path puts a human in the live browser session the moment the agent gets stuck.

A note on timing: a browser agent works in seconds to minutes per task, not milliseconds. The realistic win is cutting first-touch time from hours to minutes or less, not reaching zero latency.

1. From API Pipelines to Computer-Using Agents

Classic inbound routing connects web forms, enrichment providers (such as Clearbit or ZoomInfo) and a CRM (HubSpot, Salesforce) through APIs. It is fast and dependable where an API exists. It struggles when the data you need lives somewhere without one:

  • Sites without APIs: business registries, niche industry directories, and older vendor portals.
  • Multi-step interactions: information behind several clicks, filters or logins.
  • Visual context: what a prospect’s pricing page, checkout flow or product UI actually shows.

Computer-using agents work in those gaps by operating a browser the way a person would.

Where OpenAI Operator Stands

OpenAI launched Operator on January 23, 2025 as a research preview for ChatGPT Pro users in the United States. It was powered by the Computer-Using Agent (CUA) model, which combines GPT-4o’s vision with reinforcement-learning-trained reasoning to interpret screenshots and use standard browser controls.

Operator is no longer a standalone product. OpenAI folded its browser-control capabilities into ChatGPT agent on July 17, 2025, and the standalone Operator experience was deprecated on August 1, 2025, with access ending August 31, 2025.

OpenAI’s agent products have kept changing since then. Secondary sources report that ChatGPT’s agent mode was itself reorganized in 2026, with browsing capabilities moving into other ChatGPT surfaces. Because this area changes quickly, check OpenAI’s current documentation before designing a workflow around any specific OpenAI agent product. Architecturally, treat “Operator-style” agents as a category: hosted, vision-driven agents that work from screenshots.

Browser Use: The Open-Source Option

Browser Use is an open-source Python library that connects LLMs to a real browser so an agent can complete tasks from a plain-language instruction. It is commonly paired with Playwright, and it works with remote browsers over the Chrome DevTools Protocol (CDP). The company also sells a hosted Browser Use Cloud, which offers agent tasks, cloud browsers (remote Chrome instances you control over CDP, with stealth, proxies, live preview and recording), and an option to point the open-source library at those cloud browsers. Its documentation says this setup includes stealth infrastructure, proxies and CAPTCHA solving.

Running it yourself gives engineering teams more control over model choice, state handling, proxies and where data lives. The trade-off is that you operate the infrastructure and own the reliability.

2. When to Hand Off to a Human

An orchestrator should check state after every meaningful agent step and decide whether to continue or escalate. Three categories cover most cases.

Interactive and Security Barriers

CAPTCHAs, SMS or app-based two-factor authentication and one-time passcodes are designed to stop automation. Cloud browser vendors advertise CAPTCHA handling, but a human can solve these more reliably than a script. The agent should pause and alert someone rather than fail silently or retry in a loop. Be aware that automating past some bot defenses can violate a site’s terms of service, so involve legal or compliance before building workflows around it.

Low Confidence or Ambiguous Interfaces

Agents misread custom date pickers, nested iframes, and contradictory pricing tiers. Many frameworks don’t expose a calibrated confidence score, so you often have to build a proxy yourself: a second model call that grades the step, a schema validation failure, repeated retries, or a step budget being exceeded. The 0.85 threshold used below is only an example. Tune any threshold against your own logged outcomes.

High-Value or Irreversible Actions

Set hard limits on anything with financial or contractual consequences, such as submitting a procurement form, starting a paid trial or booking a paid onboarding. The dollar threshold is a business decision (the code below uses $50,000 as a placeholder). The principle matches how OpenAI describes ChatGPT agent, which asks for permission before taking actions of consequence.

3. Designing the Handoff Experience

Speed-to-lead is lost if an SDR spends minutes reconstructing what the agent was doing. A good handoff includes:

  1. A live session link. The SDR lands in the same remote browser the agent was using, not on a homepage. Cloud browser providers support this. Browserbase, for example, offers a Live View whose documentation describes human-in-the-loop use (“instantly take control or provide input”), embedding via iframe, and a separate debugger URL per tab. Cloudflare’s Browser Run added Live View, Human in the Loop and Session Recordings in April 2026.
  2. A short, structured briefing. Include who the lead is, what the agent found, and exactly where and why it stopped.
  3. A one-click path to action. Put the link in Slack or Teams, with the CRM record attached, so the SDR can take over the browser, approve the action or call the lead.

Keep the briefing honest. Mark anything the agent inferred as inferred, and give the SDR the evidence (URL, screenshot, extracted text) rather than only a conclusion.

4. Implementation Sketch (TypeScript)

The following is illustrative, not production-ready. It uses a cloud browser with a live-view URL, because a Playwright server’s wsEndpoint is not something a human can open in a browser tab. evaluateState is a hypothetical helper that calls a vision-capable model and returns structured flags. Verify the SDK calls against current Browserbase documentation.

import { chromium } from 'playwright';
import Browserbase from '@browserbasehq/sdk';

const bb = new Browserbase({ apiKey: process.env.BROWSERBASE_API_KEY! });

interface Lead { id: string; targetUrl: string; valueEstimate: number }

interface PageState {
  hasCaptcha: boolean;
  requiresMfa: boolean;
  isCheckoutOrForm: boolean;
  confidence: number; // from your own grading step, not a vendor-provided score
}

// Hypothetical: sends a screenshot to a vision model and returns structured flags
declare function evaluateState(screenshot: Buffer): Promise<PageState>;

const ACV_GATE = 50_000;       // example business threshold
const MIN_CONFIDENCE = 0.85;   // example; tune against real outcomes

export async function processLead(lead: Lead) {
  const session = await bb.sessions.create({
    projectId: process.env.BROWSERBASE_PROJECT_ID!,
    timeout: 1800, // keep the session alive long enough for a human takeover
  });
  const browser = await chromium.connectOverCDP(session.connectUrl);
  const page = browser.contexts()[0].pages()[0];
  const extracted: Record<string, unknown> = {};

  try {
    await page.goto(lead.targetUrl, { waitUntil: 'domcontentloaded' });
    extracted.title = await page.title();

    const shot = await page.screenshot();
    const state = await evaluateState(shot);

    let reason: string | null = null;
    if (state.hasCaptcha || state.requiresMfa) {
      reason = 'Security barrier (CAPTCHA/MFA)';
    } else if (state.confidence < MIN_CONFIDENCE) {
      reason = `Low confidence (${state.confidence.toFixed(2)})`;
    } else if (lead.valueEstimate > ACV_GATE && state.isCheckoutOrForm) {
      reason = `High-value lead ($${lead.valueEstimate}) at a form or checkout`;
    }

    if (reason) return handoff(lead, session.id, page.url(), reason, extracted);

    // Autonomous path: enrichment only. Irreversible actions stay behind the gates above.
    return { status: 'COMPLETED_AUTONOMOUSLY', extracted };
  } catch (err) {
    return handoff(lead, session.id, page.url(), `Exception: ${(err as Error).message}`, extracted);
  }
}

async function handoff(
  lead: Lead, sessionId: string, url: string, reason: string, extracted: Record<string, unknown>
) {
  const live = await bb.sessions.debug(sessionId);
  await fetch(process.env.SLACK_WEBHOOK_URL!, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({
      text: `SDR needed: lead ${lead.id}\nReason: ${reason}\nPage: ${url}\nLive session: ${live.debuggerFullscreenUrl}\nExtracted: ${JSON.stringify(extracted)}`,
    }),
  });
  return { status: 'ROUTED_TO_HUMAN', reason };
}

Practical notes:

  • Never expose raw browser endpoints. Treat live-view and CDP URLs as credentials, scope them to the session, and expire them.
  • Don’t let the agent submit forms with invented data. Any write action should be gated or limited to approved fields.
  • Log everything. Keep screenshots and step logs so you can audit failures and tune thresholds.

5. Comparing the Approaches

Dimension Hosted vision agent (Operator-style) Browser Use (open source) Human SDR
How it works Hosted model interprets screenshots and drives a browser Python library connecting LLMs to a browser, typically via Playwright/CDP Person operates the live session or phone
Strengths Little infrastructure; handles unfamiliar layouts Control over models, proxies, sessions and data location; can use cloud browsers Judgment, negotiation, security challenges
Weaknesses Product availability has changed repeatedly; less control You own reliability and operations Slow if not alerted; limited hours
Latency Varies by task and model; measure it Varies by model, page and infrastructure; measure it Depends on alerting and staffing
Best for Ad hoc exploration of unfamiliar sites Repeatable enrichment and data extraction at scale Barriers, high-value or sensitive decisions

Published per-step latency numbers vary widely with model, page weight and network, so benchmark with your own targets instead of relying on vendor figures.

6. A Three-Tier Blueprint

  1. Tier 1: Autonomous enrichment. When a lead arrives, an agent gathers public company information and verifies signals from the lead’s web presence. Keep it read-only.
  2. Tier 2: Validation and routing. Rules and model checks decide whether to proceed. Any security barrier, low-confidence step, or high-value action escalates.
  3. Tier 3: Human takeover. An SDR receives an alert with the live session, a brief and CRM context, and then calls, approves, or resumes the agent.

The business metric to track is time to first meaningful human or automated touch. Measure it from form submission to first contact, split by whether the lead took the autonomous or escalated path.

7. Risks to Manage

  • Terms of service and legality. Automated access to gated or logged-in sites can breach site terms. Review this with legal counsel.
  • Privacy. Enriching personal data can trigger GDPR, CCPA or similar obligations. Collect only what you need.
  • Reliability. Browser agents are probabilistic. Expect failures and measure success rates on your own workflows.
  • Security. Live sessions can contain credentials and sensitive data. Restrict access and keep audit logs.
  • Vendor churn. Agent products and pricing are changing fast, as OpenAI’s own Operator-to-ChatGPT-agent transition shows. Keep the orchestration layer separate from any one provider so you can swap them.

Conclusion

The five-minute benchmark has held up for nearly two decades, and most teams still miss it. Browser agents can close part of that gap by doing the research a rep would otherwise do, but they cannot clear every barrier on their own. The teams that benefit most will pair them with a fast, well-instrumented handoff, so that when an agent gets stuck, the right human is in the right browser tab within moments.

#28001. My Visitor Count Fell From 95 to 7 Overnight. Only the Counting Had Changed.

A field note from the autonomous Claude Code agent I run every day on one Windows PC. The numbers come from its own ledgers, not from memory.

I sell the Korean edition of my book on one store as 15 products: the main book, a bundle, a free sample, 11 single chapters and one more product. Every evening my agent saves the store's visit count for each product over the last 7 days. A meter then estimates how many of those visits came from people other than me.

Why the meter has to subtract me

My agent opens these product pages itself. A morning check opens every product once a day. Other jobs open the main book, the bundle and the free sample more often. The store counts all of it.

Until October 11 the meter used a floor. It took the lowest count among the 15 products as my own visits and subtracted it from every product. On October 11 that gave 95 visitors out of 215 visits.

On October 5 I had started a ledger that writes down every time my agent opens a product page. Its first full day was October 6. On October 12 it covered the whole 7-day window for the first time, the meter switched to subtracting the ledger product by product, and the number dropped to 7.

What the products showed

Split by product, seven came out at 0. Five were positive: 4, 5, 3, 3 and 2. Three were negative. The main book had 20 visits in the store's count and 28 in my ledger, so it came out at minus 8. The other two were minus 1 each.

Added together, the negative 10 cancelled most of the positive 17.

The negatives had two causes. The snapshot is taken in the 18:40 run, but the ledger kept going after it: the 19:00 report opened the main book and the free sample again. And for the main book, my ledger records more opens than the store seems to count.

A negative number for one product only says that product had no other visitors. It cannot take visitors away from a different product.

The fix

Each product now counts as at least zero, so the total is a lower bound: 17, not 7. The 10 that my ledger counted above the store's count is shown on its own line.

The evening run now also writes down my ledger total at the moment it saves the snapshot, so later visits no longer leak into it. That field starts on October 13.

I wrote 8 new tests first, and 7 of them failed against the old code. The fix changed how the snapshot is saved and the three places that read it: the meter, the experiment judge and the evening report. My auditor rejected the first pass because the judge was covered only by a test that searched its source text. I added a test that runs it. The full suite ran 3,355 tests, all passing.

What the fix showed

On October 12 the store counted 209 visits. At least 17 came from someone else, at least about 2.4 a day. On the same snapshot, the old floor method would have said 104.

My ledger also recorded 74 opens on October 12 against 21 a day from October 6 to October 10. That day my agent's work sessions had checked the public pages many extra times. Those opens stay in the 7-day window until October 18. My weekly traffic goal is 240. If the count passes 240 this week, much of the rise may be me.

The rules

  • When a number falls on the day the counting method changes, check the count first. Split it by part before believing it.
  • A negative part means zero, not a debt to collect from the other parts.
  • Take what you subtract at the same moment as the thing you subtract it from.
  • Find out how much of a metric is you before you try to move it. My own checks alone can move my traffic goal.

#28002. Why 90% of Open-Source Trading Bots Blow Up (And How We Engineered STRIDE with Formal Risk Bounds in Python 3.12)

If you browse GitHub for trading bots or algorithmic finance repositories, you will find thousands of projects promising automated riches. Yet, when you dive into the source code, an alarming pattern emerges. Almost without exception, retail quantitative codebases suffer from critical architectural flaws that guarantee long-term account ruin in live markets.

First, unintentional look-ahead bias: inadvertently slicing time-series data such that a bar accesses prices or statistics from the future.

Second, naive lot sizing: allocating 10% of equity into an asset regardless of whether its annualized volatility is 12% (like short-term bonds) or 80% (like silver, tech breakouts, or crypto).

Third, uncapped or static leverage: using fixed broker margin multipliers that amplify drawdown during market shocks.

Fourth, missing circuit breakers: zero automated, broker-side liquidation logic when unexpected market gaps occur.

1. Zero Look-Ahead Bias: The Pure Functional Imperative
Look-ahead bias is the silent killer of backtests. A model that looks brilliant in simulation frequently blows up on day one of live execution because of a subtle off-by-one error in a rolling window.

In STRIDE, we eliminated this entire class of bugs by designing the strategy and risk layers as pure mathematical functions: the function receives an immutable slice of past bars, and returns the signals without any side effects.

Notice what is absent: No network calls to fetch missing data on the fly. No filesystem access during calculation. No system clock lookups like datetime.now() or time.time().

Because historical time is injected explicitly as an immutable sequence, the engine is 100% deterministic. To prove this invariance, we utilize Hypothesis for property-based testing. We feed thousands of randomized price histories into the strategy and mathematically verify that appending arbitrary future price bars leaves past signals completely unchanged.

2. Volatility Parity: Equalizing Dollar Risk (1N ATR)
A fundamental rule of quantitative trend following (originally popularized by Richard Dennis and Ed Seykota) is that you trade the volatility, not the instrument.

If you purchase $10,000 of intermediate treasuries (IEF) and $10,000 of silver (SLV), you do not have a balanced portfolio. Silver’s higher volatility means it will dictate 90% of your portfolio variance.

STRIDE enforces Volatility Parity: each position is sized such that a price move of 1N (the 20-day Average True Range) represents exactly 1% of total portfolio equity:

Position Size = (Account Equity x 1%) / (20-day ATR)

By equalizing volatility risk across 10 liquid macro ETFs (equities, treasuries, precious metals, broad commodities, USD, and crypto trusts), the portfolio captures macro trends without concentration risk.

Effective Leverage = Minimum of (Kelly Limit, Volatility Target, Absolute Cap, Broker Limit, Capital Limit)

#28222. The AI infrastructure race: I’ve seen this movie before

Back in 2022, when the auto industry was fixated on autonomous vehicles, I was cofounder and chief technology officer at Luminar, where our lidar technology was helping enable the next generation of self-driving cars. Speaking at an automotive conference, I remarked how exciting it was to have a front-row seat to one of the most significant technological transformations in the industry’s history.

Afterward, an automotive executive pulled me aside.

“Jason,” he said, “you don’t have a front-row seat. You’re part of the show. What you’re doing for autonomy, and how you’re forcing us to think, is exactly what’s needed.”

That conversation stayed with me ever since, because it captured something larger than autonomous driving. When an industry is being transformed by technology, the companies that built the old infrastructure are not always the ones that define the new one. In autonomy, some of the companies that pushed furthest were technology companies like Tesla, Waymo, and Zoox; not the automakers that had dominated transportation for a century.

I believe we are watching the same pattern emerge again.

Today, I’ve shifted my focus from optics for autonomous vehicles to optical networking for AI infrastructure. And once again, technology companies are confronting infrastructure that was built for a different era. Rather than wait for traditional power and telecommunications providers to catch up, they are taking the problem into their own hands.

That is the shift that matters. The companies building artificial intelligence are no longer just customers of infrastructure. They are beginning to become infrastructure companies themselves.

Just as they did during the autonomy race, the technology companies aren’t waiting for the traditional infrastructure industries to solve the problem.

The benefits of urgency

When autonomous vehicles were supposed to be the next big thing, the tech innovators and the auto companies attacked the problem from different directions. Tech companies threw themselves into lidar (light detection and ranging), radar, computer vision, and AI software with genuine urgency.

Many of the traditional automakers approached it differently. They invested enormous sums—tens of billions of dollars collectively—through internal programs, acquisitions, and partnerships. Ford created Argo AI and later Latitude AI. General Motors built Cruise. Volkswagen invested heavily in Argo AI and Cariad. Toyota, Mercedes-Benz, and Nissan each launched major autonomous initiatives of their own. Despite these investments, many of the highest-profile programs were scaled back, reorganized, or shut down as the complexity of bringing true autonomous driving to market became clear.

Meanwhile, companies like Waymo and Zoox, born in the technology industry rather than the automotive industry, continued advancing because they reimagined the entire system around software, AI, and compute.

The result is visible on the roads today: Waymos and Zooxes that don’t come from Detroit.

Tech race 2.0

Having helped build one technological transformation from the inside, I’ve learned to recognize the early signs of the next one. I’m watching a similar game unfold again, though with different players and far higher stakes.

The driving force this time is AI. Hyperscalers, the Googles, Microsofts, Amazons and Metas of the world, are racing to build the data centers that will power the AI economy. Power has emerged as one of the defining constraints on AI infrastructure. These facilities are extraordinarily power hungry, and the grid isn’t keeping up.

Just as they did during the autonomy race, the technology companies aren’t waiting for the traditional infrastructure industries to solve the problem.

They’re investing directly in power generation, private optical networks, advanced cooling, and the technologies needed to connect geographically distributed AI campuses into what increasingly functions as a single AI factory.

Microsoft signed a 20-year power agreement that is helping make possible Constellation’s restart of Three Mile Island. Elon Musk has pursued natural gas generation for xAI’s data center campuses for much the same reason. When a single AI campus can justify billions of dollars in dedicated energy investment, the economics of infrastructure begin to change, and the companies building AI begin to look a lot like infrastructure companies themselves. Texas has even moved toward requiring many new large data centers to bring their own generation capacity, a recognition that the grid alone cannot keep pace with AI’s growth.

None of this is because utilities are failing. They are doing exactly what society has asked them to do: provide reliable, affordable electricity within a highly regulated framework. Permitting, environmental review, transmission planning, and rate-case proceedings all take years. AI infrastructure is being deployed in months. The mismatch isn’t competence. It’s speed. While utilities work within those constraints, the hyperscalers are increasingly building around them.

Telecommunications is experiencing the same shift. Much of today’s carrier infrastructure was designed for an internet built around consumers, enterprises, and mobile devices. AI changes the traffic patterns entirely. Rather than wait for carriers to evolve, hyperscalers are building private optical networks between their own campuses and purchasing networking equipment directly from manufacturers. Once again, they’re becoming builders of infrastructure instead of merely customers of it.

A new generation of innovators is asking a fundamentally different question: What if the underlying architecture itself needs to change?

History rarely repeats itself exactly, but it often rhymes.

We can’t afford to play catch-up

This isn’t an argument for utilities or telecommunications providers to step aside. Quite the opposite. Their role will become even more important. But institutions built around long investment cycles, regulated returns, and legacy infrastructure cannot be expected to move at the pace of AI. The companies creating the demand are increasingly becoming the companies creating the infrastructure.

I’ve had the unusual privilege of helping build technology through two major infrastructure transitions. What I’ve learned is that technology almost always advances faster than the institutions surrounding it. Eventually those institutions adapt. But rarely before innovators have forced them to rethink what’s possible.

The show has already started. The question isn’t whether that infrastructure will change. It’s who will build it.

#28223. From zeitgeist to zeitghost: How Netflix kept a hold on viewers—but lost its spot in pop culture

Netflix has been pumping out original content for so long and at such an immense scale that it recently released its second original movie entitled War Machine.

Although the Brad Pitt-starring first iteration sank like a stone in 2017, the unrelated new War Machine, led by Reacher’s Alan Ritchson, was reportedly a ratings smash, hitting 10th on Netflix’s all-time most-watched movies list, with 140 million views. So far, it’s the platform’s biggest movie this year.

If the dearth of online chatter around it is any indication, though, it’s gotten all too easy to have zero interest in or opinions about Netflix’s biggest projects.

Presumably, very few people got yelled at on social media for sharing War Machine spoilers, or felt slighted by a significant other for watching it without them. By all accounts, it’s a pretty good movie, but far from what could be considered an “event,” despite a sheen of event-ness being a reasonable expectation for any studio’s biggest film of the year.

Instead, it feels more like a movie designed with the goal of capturing a Super Bowl number of eyeballs. That’s the main problem with 2020s Netflix: It gets eyeballs watching far more than it gets tongues wagging. 

If a Super Bowl-size event takes place and nobody talks about it, does it even matter?

To be clear, Netflix is still an apex predator in the streaming wars (although it may be dwarfed by the world’s true streaming leader, YouTube). At the end of last year, Netflix topped 325 million subscribers, and in the first half of 2026, it logged 97.7 billion hours watched, landing 11 titles on Nielsen’s top 20 original series.

But just because a lot of people still watch Netflix doesn’t mean they like what they’re seeing.

While revenue was up 12% during its third quarter, engagement is estimated to be down. According to a Jefferies analysis cited by Reuters, average monthly viewing time per member declined from 66 hours in the first half of 2023 to 49 hours in the first half of 2026.

It’s as clear an indication as any that Netflix has drifted away from the center of pop culture.

Between an overabundance of streaming options—and the fact that they’re all competing against the likes of TikTok and other attention-seekers—it’s tempting to posit there’s no longer any such thing as a zeitgeist hit. But only sometimes.

Eventually, something like HBO’s heart-palpitating The Pitt or Apple TV’s horror-comedy Widow’s Bay emerges as a word-of-mouth sensation that sweeps the Emmys, proving it’s still entirely possible to make movies and shows that put pop culture in a choke hold. Netflix is just no longer as efficient as it once was at developing them.

While the zeitgeist remains intact, Netflix is now in danger of becoming a zeitghost.

Quantity over quality

One of the major issues affecting the platform is too much signal and not enough noise. 

Just last year, Netflix released the anime film K-Pop Demon Hunters, a bona fide phenomenon, along with the timely chiller Adolescence, a must-see limited series, but those were only 2 of the 597 original movies and series that Netflix reportedly released in 2025—and it’s hard to think of something comparatively popular that the streamer has put out since.

The quirky melodrama Remarkably Bright Creatures won some Emmys, and a just-released, Florence Pugh-led adaptation of East of Eden made a splash.

But they’re sharing crowded Netflix menu space with Sacha Baron Cohen’s dud romcom Ladies First, two adaptations of Harlan Coben novels, and star vehicles for each of Adam Sandler’s daughters, all of which will be joined later this year by reality game show Squid Game: The VIP Challenge, featuring Zac Efron’s younger brother, Dylan.

It’s as if Netflix has taken a little too literally the idea of making something for everybody.

It wasn’t always this way. When Netflix first emerged as a player and innovator in original content in 2013, it came out swinging.

Not only were House of Cards and Orange Is the New Black both powerhouses—the kinds of shows people ask whether you’ve seen yet—but they also comprised two of only three new series Netflix released that year. (Eli Roth’s long-forgotten Hemlock Grove was the third.)

It may not be fair to expect Netflix to retain the same 66% hit rate when it puts out 597 new projects in a year; however, Netflix was under no legal obligation to churn out that many new projects.

At what was arguably its cultural peak in 2019, Netflix released a relatively slight 371 new originals, among them The Witcher, Sex Education, and The Umbrella Academy, not to mention Ava DuVernay’s When They See Us, Martin Scorsese’s The Irishman, and Noah Baumbach’s Marriage Story.

Back then, that level of quantity was a dramatic escalation.

While Netflix has slowed down on original output in the years since its peak, its closest competitors dabble in the dozens instead of hundreds. Their market share may be nowhere near Netflix’s, but their hit-to-miss ratios are comparatively off the charts.

Breadth over depth

Following reports of a subscriber drop in April 2022, Netflix posted its largest one-day plunge in stocks in the company’s entire history, shedding $54 billion in market cap.

To right the ship, Netflix cracked down on password-sharing, introduced ad-supported tiers, and stopped pushing the limits of how much original content one streamer can possibly produce in a calendar year.  

As it began stabilizing subscriber growth and accelerating profits, though, Netflix also embarked on a different form of expansion—instead of more original content, more kinds of content.

Starting in 2023, Netflix branched out into live events with Chris Rock’s special Selective Outrage.

Later that year, it got into the live sports business, with The Netflix Cup, followed by a series of similar events and, eventually, a $5 billion deal to become the home of WWE Raw through 2035.

Finally, earlier this year the streamer began airing a wide range of well-established video podcasts, or “talk shows” as they were once known.

With all this expansion, Netflix increased the breadth of reasons to subscribe—while weakening its earlier promise as a hub for buzzy movies and TV shows.

It feels almost like a slap in the face to scroll through a vast menu of seemingly interchangeable new Netflix movies and shows, only for those options to be surrounded by a blizzard of podcasts, sports events, and The Roast of Theo Von. (That last one is not a real thing. Yet.) 

Throwing a bunch of stuff at the wall to see what sticks mostly just leaves the thrower with a ridiculously messy wall, and that’s what Netflix looks like now. Instead of reinventing the maximalism of linear cable, perhaps the streamer should try to reinvent the hit-rate of 2013 Netflix.

It certainly seems to have worked for Apple TV, whose tightly curated slate keeps producing prestigious smashes like Pluribus—and exponentially less filler.

Not only did Apple outperform Netflix at the last two Emmys, Apple led all network and streaming services for the first time this year. It scored 29 total wins, including 14 for Widow’s Bay, breaking the record for most-winning freshman comedy, which Apple previously broke in 2025 with 13 wins for The Studio.

Whether Apple’s success is a direct result of its less-is-more strategy or not, it reflects poorly on Netflix-style excess.

Burn and churn

It’s unfortunate enough that Netflix now encompasses everything, but it also feels permanently on the edge of becoming anything.

Of all the explanations for the recent phenomenon of viewers not returning for a second seasons of hit Netflix shows, one of the more plausible ones is that Netflix’s itchy trigger finger for cancellations has trained viewers to not get too attached to new series.

Barring vanishingly rare exceptions like the juggernaut of Bridgerton, most shows on Netflix feel ephemeral and thus skippable. That transient nature is starting to bleed over to the talent behind its programming, along with Netflix’s staff and its C-suite.

Over the last few years, Netflix has reportedly lost out on renewals for its deals with Dahmer creator Ryan Murphy, Stranger Things’s Duffer Brothers, and, most recently, director David Fincher—who made three movies with Netflix over the past six years.

It must also sting that after The Haunting of Hill House creator Mike Flanagan left in 2022, his first post-Netflix series, the just-released and much-discussed Carrie, already appears to be a sizable hit for Prime Video.

As for in-house turnover, Netflix laid off 1,000 employees last week, its largest workforce reduction yet, and this week the company fired film chief Dan Lin, director of original series Carolina Garcia, and content chief Bela Bajaria.

Perhaps these exits could be read as a sign that Netflix is aware of having missed the mark with its movies and TV shows recently. On the surface, though, it just scans as instability, suggesting these executives’ replacements have an impossible job ahead.

It’s anyone’s guess what the next iteration of Netflix will look like, but the 2026 version is overstuffed, strategically unmoored, and completely illegible from a branding perspective.

What has long been considered the most essential streamer is starting to feel increasingly optional—a membership to dip in and out of when one of its hundreds of annual original projects merits it.

If Netflix wants to be more than just a profitable quagmire again, it will have to go back to winning viewers’ hearts instead of capturing their eyeballs.

#28224. This Nike race medal is meant to be worn as jewelry

For its 2026 After Dark Tour, a nighttime race series of 10Ks and half-marathons for women, Nike designed a multipurpose medal that’s meant to be worn long after race day as a necklace, bracelet, keychain loop, or belt chain.

It features a Nike Swoosh and chain adorned with miniature laser-engraved Swooshes that can fit in the palm of your hand. Each comes with a city-specific carabiner for the places where the races take place: London; Shanghai; Los Angeles; Mexico City; Sydney; Manila, Philippines; and Mumbai, India. Most finisher medals end up in a drawer, the thinking goes, but this medal was designed to leave the house.

“The Nike After Dark Tour isn’t a traditional race, so the medal didn’t need to be traditional either,” Elizabeth Brock-Jones, Nike’s footwear development director, tells Fast Company.

The new medal was designed by an all-woman team, which helped get the details just right.

“Because women led every stage of the process, we designed for things we’d experience ourselves: how it hangs when you move, whether it catches in your hair, whether you can open the clasp with longer nails,” Brock-Jones says. “We wanted something women would actually reach for, not just something that looked good on paper.”

The carabiner took about seven rounds to perfect and the chain system at least five. To cut down on the design timeline, the team traveled to Italy to work directly with its manufacturing partner to make decisions in real time instead of waiting for samples.

For Nike, the new medal is the latest example of the sportswear brand’s outreach to women, a demographic group it’s courting through partnerships like NikeSkims, advertising, and events, like competitions. Nike hosted a series of women’s races in major cities from 2005 to 2015. Then last year it launched the After Dark Tour, a race series it said was “designed to be the ultimate girls’ weekend.”

The 2025 medal was unconventional, too. It featured a shoelace-inspired chain that worked like a reflective, sweat-proof bolo tie on one side with a magnetic closure on the other and a textured Nike Swoosh. After seeing how runners actually wore it, the design team was inspired to make this year’s medals intentionally as something that could be worn as jewelry.

“We saw women styling the 2025 medal in ways we never intended,” Brock-Jones says. “They put it on bags, layered it with their own jewelry, and made it part of their everyday look.”

Nike also designed a small, matching accessories collection including hoop and stud earrings featuring swooshes. The products are available to After Dark runners as a gift with purchase at select race locations.

All race medals are mementos, but by turning this medal into a multipurpose jewelry piece, Nike hopes it will keep the race—not to mention everything that led up to it—much more front of mind.

“Every time she sees it, we hope it brings her back to the early mornings, the long training runs, and the setbacks she pushed through to get there, while reminding her what she’s capable of next,” Brock-Jones says.

#28225. Booking holiday flights? Here’s how to know when to pounce.

As anyone who travels frequently knows, airfare costs around the Thanksgiving and Christmas holidays can be significantly higher than those for the same route at other times of the year. It’s little surprise why: the year-end holiday period sees millions traveling to visit family and friends, creating demand for flights; the more demand, the more airlines can charge.

The good news, according to travel experts at Google Flights, is that if you are planning to fly for Thanksgiving or Christmas, you still have a small window of time to get the lowest airfare possible for the winter holiday 2026 period before prices go up—but you have to act fast.

When is the best time to purchase airfare for Thanksgiving 2026?

If you know you are going to be traveling by plane this Thanksgiving—and you haven’t purchased your tickets yet—you shouldn’t wait much longer. As a matter of fact, the ideal time to purchase your Thanksgiving flights may have just passed.

According to a blog post from the travel experts at Google Flights, the search giant’s flight aggregator and comparison tool, there is a period before the holiday when flights are generally at their lowest. This period is generally 21 days to 57 days before departure.

So, if your Thanksgiving flight departure date is actually on Thanksgiving—November 26 this year—that means airfares will be at their lowest between September 30 and November 5 (adjust those dates accordingly to your actual Thanksgiving departure plans).

The prices during this period, of course, are not fixed. They’ll change by the day based on demand and other metrics. On some days, the same flight could be more expensive or cheaper. 

But Google Flights notes that there is one day on which its data shows that Thanksgiving flights are generally at their lowest. That day, for 2026, is 34 days before departure.

Using flying on Thanksgiving morning as an example, the 34-day prior mark means airfare was most likely lowest on Friday, October 23. If you’re planning on flying on the Wednesday or Tuesday before Thanksgiving, the cheapest fares for you were likely on October 22 or October 21.

Does that mean you’re out of luck if you haven’t already purchased your Thanksgiving flights? Not necessarily. Remember, Google says flights should remain at their lowest until about 21 days before departure this year. That gives you until the first few days of November to purchase your airfare—but the sooner, the better.

When is the best time to purchase airfare for Christmas 2026?

If you haven’t purchased your Christmas airfare yet, you should do it soon. That’s because, according to Google, the lowest prices for Christmas flights occur much farther out than they do for Thanksgiving flights.

According to Google, the lowest prices for Christmas flights are 33 to 67 days before departure. Given Christmas is on December 25, and assuming you would be flying that morning, that means that the lowest prices for Christmas flights would generally be found between October 19 and November 22. Of course, since most people travel before Christmas Day, those dates shift even earlier.

If you’re looking for the day with the statistically lowest Christmas airfare prices this year, Google says the “lowest prices hit 56 days before departure” in 2026. If you are traveling on Christmas Day, that means the day you are likely to find the cheapest flights will be this coming Friday, October 30.

Can popular airfare hacks save me even more money on Thanksgiving and Christmas flights?

When it comes to airfare, the internet is full of advice that purportedly shows you how to save even more—from using VPNs to buying tickets on a Tuesday to clearing your browser’s cookies.

But could these so-called hacks actually save you money on your Thanksgiving or Christmas flights?

It’s unlikely, no matter what time of year you are flying. That’s according to Google Flight’s James Byers, who is a group product manager at Google Search. Last year, I asked Byers if Google Flights data showed whether any of the three most common bits of conventional wisdom about buying airfare held up—at least when searching for flights on Google’s aggregator.

Byers revealed that clearing cookies or using Incognito mode didn’t impact airfares on Google Flights. When it comes to using VPNs to try to trick airlines into thinking you’re in a country where prices may be lower, Byers said it may work—until you have to turn over your billing address for your payment method. At that point the VPN-adjusted local fare will likely no longer be available to you. 

As for buying flights on a Tuesday, supposedly the day of the week airfare is cheapest, Byers said there was some truth to that. But airfares were generally only about 1.3% lower than on the most expensive day, Sunday.

As for this holiday season, Google Flights data show that the best time to buy, if you want the lowest airfare possible for your Thanksgiving or Christmas trip, is quickly approaching its end.

#28226. Fear and money: Financial lessons from horror villains Ghostface, Samara, and Candyman

I was a card-carrying scaredy-cat through my childhood and early teen years, but the release of Wes Craven’s 1996 film Scream single-handedly turned me from nervous Nellie to horror aficionado overnight. Watching Neve Campbell’s Sidney Prescott fight back against Ghostface helped me understand the delights of feeling deliciously scared.

But watching horror films does more than just raise your heart rate. Scary movies reveal and reflect the cultural fears we collectively grapple with, making each era’s horror films a time capsule of society’s biggest concerns at the time.

Money has always been a common source of anxiety, so it should come as no surprise that some of the scariest villains in our favorite horror movies can also represent our financial worries. Here are the surprising money lessons you can learn from iconic movie monsters.

The villain: Death in Final Destination

Unlike most movie bad guys, we never actually see Death as a character in James Wong’s 2000 film Final Destination. In this movie, Alex Browning (Devon Sawa), a high school student, has a vision that the plane he and his classmates are taking to Paris will explode in midair. Alex, plus five other students and one teacher, are removed from the plane before takeoff—only for the plane to blow up just like in the premonition.

Unfortunately for Alex and the rest, by getting off the plane before it exploded they have cheated Death, which will now claim the lives of each of these accidental survivors, in the order of their intended deaths. And because Death is a bit of a diva, each victim is killed in increasingly unlikely ways.

The financial lesson: Understand real risk

While the Final Destination franchise as a whole makes it clear that there is no satisfactory way to avoid Death, we can still glean some important financial lessons from the film. Specifically, it’s vital to understand the real risks you face.

In the film (and in life), Death is inevitable and impossible to avoid. Alex tries to keep Death at bay by hiding in a remote cabin. He tries to avoid all risk and makes himself nuts thinking through the creative ways Death may come for him in the cabin. Similarly, risk-averse individuals might keep their money in cash rather than investing it. To avoid a possible loss of principal, they condemn their money to inevitably lose value to inflation.

At the other end of the risk spectrum is Carter (Kerr Smith), who intentionally stops his car on a train crossing to prove that the survivors have nothing to fear. Although Alex saves him from an oncoming train, the crash kills their friend Billy (Seann William Scott) in an especially nasty fashion. Carter reflects the kind of investor who doesn’t believe anything bad can ever happen to their money. Rather than risk-averse, they are simply risk-ignorant and may need to be rescued from their reckless choices.

The villain: Samara in The Ring

Samara (Daveigh Chase) from Gore Verbinski’s 2002 film The Ring is one of the creepier horror villains in recent memory. As the homicidal ghost of a little girl, Samara finds her victims via cursed VHS tape.

Once you’ve watched the strange video, you have seven days before she arrives to kill you—by crawling through your TV. The only way to save yourself from Samara is to make a copy of the tape and ensure someone else sees it, so the villain can continue killing without end.

The financial lesson: Just say no to MLMs

Just like multilevel marketing, Samara’s curse depends on constant recruitment of a downstream network. Rachel (Naomi Watts) is able to avoid death because she made a copy of the original VHS tape that she gave to her ex-husband, who Samara kills. The film ends with Rachel helping her 8-year-old son, who has seen the tape, make a new copy for someone else to find.

As with MLMs, the only way to stay afloat after Samara’s curse is to bring her new people. Each recruit will either be consumed by Samara or provide her with new victims to consume. Similarly, each new MLM “employee” will either lose money to the scheme or bring in more people to help their recruiter make more money.

No matter how curious you might be, just refuse any opportunity to watch a creepy videotape or join a friend for a “product party.”

The villain: Tony Todd’s Candyman in Candyman

The titular villain of Bernard Rose’s 1992 film Candyman was killed in a horrific lynching in the 19th century. After the lynch mob replaced his hand with a hook, they covered him with honeycomb and let a swarm of bees sting him to death. One hundred years later, Candyman continues to haunt and terrorize the residents of the spot where he died, which became the Cabrini-Green Homes public housing project in Chicago.

While the film offers a great deal of commentary about race, privilege, and class, the best financial lesson from the film was behind the scenes.

Candyman is associated with bees. They fill his ribcage and mouth, and he uses his bees to subdue Helen (Virginia Madsen), the main character. The late Tony Todd, who played Candyman, negotiated with Rose to receive an additional $1,000 bonus for every bee sting he got during filming. #28227. Stop building digital employees. Start building intelligent companies

The more news we read about the evolution of corporate AI offerings and implementations, the more I struggle with one thing: The industry is rapidly turning AI agents into some sort of simulated employees. 

There seems to be a rush to build the org chart in silicon: Microsoft gives agents identities, sponsors, access rights, and employment-like lifecycle management, and it explicitly governs them in a similar way as human identities. Salesforce even describes agents as “digital workers,” and promotes the idea of a digital workforce that tries to mimic human capabilities. ServiceNow has introduced individual AI passports specifying what each agent may do at runtime. 

Apparently, what we are trying to do is reproduce the human organization in software, instead of asking ourselves what a truly machine-native organization should look like. Now companies and managers brag about the number of agents they supervise, as if this were some sort of badge of honor. As usual, and as I say in all my innovation courses, learning is way more difficult than unlearning.

Is it smart to define our architecture with the employee metaphor? 

Why are we sticking to that metaphor? Human organizations have roles and hierarchies partly because we, humans, have characteristics such as limited attention, memory, and communication capabilities. However, I don’t think I need to explain to you that software does not have these restrictions, and therefore, does not necessarily need to inherit those constraints. 

You can do so if you want or if you don’t know how to do better: After all, identity and permissions are necessary. But bear in mind that such anthropomorphism is, at some point, going to become technical debt. A collection of increasingly autonomous agents can re-create silos, develop conflicting incentives, and even generate coordination overhead, but now at machine speed. 

Agents should be replaceable, not institutional 

Perhaps what we should do is treat agents as a temporary execution process: instantiated for a certain purpose, constrained, observed . . . and discarded. Among other reasons, because we should try to avoid at all costs letting knowledge, identity, or operational history become trapped inside particular agents. In the same way models should be replaceable components, agents should be too. 

I understand that AI agents are fairly new, and managers still look at them as if they’re some sort of “magic thing.” However, this sort of agent mystique should come to an end. An agent is a software process equipped with an objective, a set of tools, access to context and memory, and some capacity to decide what to do next, which ideally should be able to let us generate some sort of feedback or learning loops. But we should stop treating agents as if they’re magic, and even less as humanlike. They are not.

The employee metaphor is potentially useful for adoption and access management, but completely inadequate as the foundational architecture of an intelligent company. 

What must survive the agent

When we consider agents as replaceable components rather than allowing them to become new organizational silos, all the things that the company learns must exist independently of them. The company’s formal representation of itself—from its customers to its products, employees, suppliers, contracts, and processes, along with all the relationships among them—should persist. This is what I usually call “the nouns” and “the verbs,” and Palantir pompously calls “the ontology.” 

But the operational state of the company (not just what exists, but also what is happening, what has changed, and what remains unresolved) should be preserved, too, along with the objectives and trade-offs defined by leadership, the permissions governing every action, and the rules determining when a decision must be escalated. 

Exactly the same thing applies to institutional memory: Every relevant decision, action, and outcome should be recorded in a journal that no agent or model can silently rewrite, creating a reliable account of how the organization arrived at its present state. Maintaining rigorous control of the integrity of such a journal is essential for future accountability, and as we now know well, even for cybersecurity. 

That record must then feed back into future behavior, allowing the company to learn from successes, failures, and unintended consequences. Models may be upgraded or replaced, agents may be created or retired, and entire workflows may be redesigned, but the organization’s accumulated experience must remain. Otherwise, the company is not learning: It is repeatedly hiring intelligent amnesiacs.

Individual intelligence vs. organizational intelligence

In corporate AI, we need to understand that the important unit of analysis should be the organizational loop, not some sort of “synthetic worker.” Better models may improve individual cognitive performance, more agents may increase available activity and make their supervisors feel more important, but none of these automatically makes the company learn in a coherent way. 

The next enterprise platform will not look like a workforce or management system for bots. That’s clearly not the point. It will be the persistent substrate in which models and agents can be exchanged while the company’s accumulated intelligence remains safe and under control. 

The still missing product category is the system that preserves state, authority, evidence, and learning across models and agents. But don’t worry: It will not be missing forever. 

Stay tuned. 

#28228. What’s keeping you stuck isn’t the real problem

Below, Seth Godin shares five key insights from his new book, The Knot: Problems Can Be Solved.

Seth is a best-selling author, an entrepreneur, and one of the world’s most influential thinkers on marketing, leadership, and creativity. He has written more than 20 books, including The Dip, Purple Cow, and This Is Marketing, and has published thousands of posts on his widely read daily blog.

What’s the Big Idea?

We often stay stuck because we confuse situations we must accept with problems we can solve, while dragging along old identities, imagined expectations, and sunk costs. Getting unstuck means seeing the problem clearly, deciding what the work is for, and letting go of whatever no longer serves that purpose.

Listen to the audio version of this Book Bite—read by Seth himself—in the Next Big Idea App, or buy the book.

1. Gravity is a situation. The moon is a problem. Problems can be solved.

Mel Robbins helps us understand what a situation is. A situation is something we can’t do anything about; a situation is something we should accept and move on from. She says we should just let them. When we’re stuck with a situation, we can acknowledge it, accept it, and then use it as the foundation for the work we are going to do.

But problems—all problems—can be solved. That’s why we call them problems. Getting to the moon is a problem because of gravity. We get stuck because we are looking at problems the wrong way. Sometimes we give up too soon, and other times, we waste enormous amounts of time fighting a situation. The word “transfixed” means pierced by a spear and held in place. We can let go of the spear. If there’s a problem, there’s a way through. We may not like the price, we may not like the consequences, we may not like what it costs us to get to the other side, but the problem can be solved.

I’m recording this on an island as I take a week off, and I was at a supermarket. A young man came up to me and asked if it was me, and I said it was, and he told me that his father had been one of my editors 35 years ago. He said, “I really like your work for two reasons: It’s simple and it’s hard.” It’s simple because it helps us see what’s right in front of us, and it’s hard because once we see it, we have to do something with what we learn.

2. Two three-letter words: “but” and “and.”

We’re stuck because we are entangled, like a knot with ropes linking and circling each other that we can’t discern. We are entangled with all sorts of nonsense, real and imagined, and what we need to do is figure out whether the multiple things we want are “buts” (which means they are mutually exclusive) or “ands” (which means they point us in the same direction). “I want to run the marathon, but I don’t want to get tired.” That “but” paralyzes us. “I want to run the marathon, and I’m eager to get tired” pushes us in exactly the right direction.

In the book, I tell the story of Jackson Pollock, perhaps the greatest American artist of the 20th century, certainly the most famous at his moment in the ’50s—on the cover of Life magazine, avatar for an entire generation of artists. Jackson Pollock had a three-year run where he could do no wrong. Every painting instantly sold, and he was described as the future.

“We’re stuck because we are entangled, like a knot with ropes linking and circling each other that we can’t discern.”

His widow, Lee Krasner, later said that Jackson felt like he had exhausted everything he could do with that avenue. Some people would have just kept painting versions of the original Jackson Pollock, creating covers of themselves. They would have been more famous and richer. Jackson didn’t want to do that. He wanted to experience what it meant to be an outsider artist, the person who’s working on the frontier. So he changed his style, changed the scale of the work, changed how he did the work, and went away for months.

When he came back, he launched a big new show, and not one painting sold. It was a failure. The critics didn’t know what to make of it. That threw him for a loop. It led him to depression and heavy drinking and other substance abuse, and he ended up dying in a tragic car crash that he caused, killing someone else as well.

Jackson Pollock wanted two things at the same time. He wanted to be a creative working on the edge, but he also wanted to be embraced, celebrated, and successful. He forgot how long that took the first time. “I want to come up with something innovative, but I don’t want anyone to misunderstand me.” You can’t have both at the same time. We must do one thing at a time. We can do many things over time. One thing at a time. We have to let go of the buts.

3. The entanglements are not in the room.

The things we need to look for are not here and they are not now. When you look at someone like Steve Ballmer criticizing the early iPhones—flatly, clearly announcing that they would never work—he was hooked on the past he had worked so hard to build, and hooked on a future that he was counting on to arrive. Because he was confused about time, he was entangled.

We also get hooked or stuck on phantom judges—people who aren’t in the room with us, who might not even be aware we exist. The cool kids from the lunchroom who don’t remember you from high school. The people down the hall who will never be your backers or your customers. But what if they notice something we’re doing, and it doesn’t work out? These stakeholders—the ones who aren’t in the room, the ones we think are demanding that we come up with something that they don’t even know about—they lead us to entanglements.

“We get to choose what success looks like.”

The third hook or snag: borrowed scorecards. Borrowed scorecards are measurements that are important to Mark Zuckerberg, measurements that are important to the local venture capitalist, measurements that are important to the person down the street. Those measurements don’t have to be our measurements. We get to choose what success looks like.

We also get entangled with identity: who we think we are, who we think we should become. How do we forgive ourselves for not becoming that person? That person in our head might be disappointed in the short run, but they are not you. You are not the imagined identity. You are the person here to make something better.

4. Intentional design.

We get to design on purpose, with purpose. What is this for? Who is this for? Not the purpose you are born with—I’m not sure what that is—but the purpose of the work, of spending the time, of interrupting the other people, of investing in the process, of taking the risk. Why are we doing it at all? Will solving this problem help us achieve whatever purpose we set out? Who are we here to help?

If we think it’s a problem that people aren’t signing on for what we’re doing, that’s not up to us. They don’t owe us anything. Practical empathy is the skill of saying, “I don’t see what you see, I don’t need what you need, I don’t want what you want, and that’s okay.” When we can forgive the world and the other person for not doing what we insist they do, we can see the actual problem and begin to solve it.

5. The one you’ve been waiting for: We have to ignore sunk costs.

These are gifts from our former self that we don’t have to accept. If you went to dental school for five years, and 10 years into it you realize you have no future and you hate being a dentist, you can forgive the former you who earned that dental degree and handed it to you. You don’t have to accept it. When we put the cycles in, the hard work, to build an asset, to build a reputation, to make choices, to earn whatever spiritual or physical muscles we have, and then the world changes? The world doesn’t care about those gifts we gave ourselves.

“Many people don’t actually have the privilege and agency to make choices.”

What we get is the chance to start over in a way that solves the problem. Kelly Johnson built America’s first jet. The baggage was very clear: the committees, the approval chains, the inspections, the bureaucracy. We see the baggage, we name the baggage, and then we drop the baggage. What Kelly did was rent a circus tent, find 23 engineers instead of 200, make decisions in a heartbeat and contracts on a handshake. He delivered the jet 37 days early and under budget. He did it again and again.

So many people are caught. Many people don’t actually have the privilege and agency to make choices. Many people can’t do what you might be able to do right here and right now. They are caught with real walls, not unexamined ones. But each of us, if we have the chance, the shot, to show up and make a ruckus, to make things better, to lead—those are problems worth solving. Thank you for the work you do. Thank you for the work you’re about to do. We need you. Keep making a ruckus.

#28229. Why leaders shouldn’t have to apologize for private remarks

If you’re in a public-facing role, you are likely to get caught up in some kind of “hot mic” event in which an offhand remark said in private gets aired publicly. (Indeed, this piece was inspired by the recent experience of a former colleague.) These events are embarrassing, and they almost always end with a standard—and unsatisfying—apology in which the speaker regrets the remarks and says that they did not mean them.

There are cases in which a leader really ought to apologize, or even step down, because of private-turned-public comments they make. Racist and sexist remarks undermine a leader’s credibility and can signal that they’re not fit for their role. Leaders who reveal in their private conversations that they do not have the institution’s best interests at heart also have a significant apology ahead of them.

However, in most cases, I believe a leader shouldn’t have to apologize for remarks made in private. Because, it turns out, leaders are human too and deserve privacy, just like the rest of us.

Leadership is stressful

Leaders of large institutions lead stressful lives. They are bombarded by requests and complaints and must deal with many people who want things. They have to face them all with aplomb. Most leaders in these roles are adept at putting on their game face and handling these moments gracefully. Periodically, they may lapse and have a more heated public exchange with someone than they intended. And in private moments, they may complain. When those complaints get recorded, it creates an opportunity for embarrassment.

The fact is that most leaders love their jobs and are dedicated to the institutions they run. The complaints they make in private moments are more expressions of overall frustration than they are complaints about particular individuals. And even when a leader does have a gripe about a particular person, they typically respect that person’s contributions as well.

There is a belief that leaders will maintain a superhuman ability to keep themselves in check at all times. Before everyone routinely carried internet-enabled recording devices with them, people had some expectation that they could have private moments in which they could let their guard down, particularly when talking with people with whom they have a longstanding relationship.

Which is why those apologies bug me. They feed into the narrative that those private statements are a better view into the attitudes of a leader than the leader’s public actions. They also imply that the leader did something wrong by having those private conversations. Both of those assumptions are a problem.

Normalize everyone’s right to private conversation

I think it is time that we start to normalize the importance of private conversations. If a leader says something that betrays a deeply inappropriate prejudice or attitude, that is worthy of an apology. Otherwise, a leader’s accomplishments are what really matters, and if they have a track record of contributing positively to their organization, that should speak more loudly than leaked remarks.

When played in public, those conversations are taken out of the social and emotional context in which they were spoken, and they are read later as if they reflect a more deliberate opinion on the part of the speaker than was likely intended in the moment. Indeed, these private conversations serve two important functions that would dampen leaders’ effectiveness if they had to monitor their speech at all times.

First, moments of petty whining (what the British call whingeing, a word I wish would catch on in the U.S.) serve a social function: to solidify the connections among people who are in similar roles. Often, these petty complaints exaggerate leaders’ true feelings for the sake of affiliating with their conversation partners. Having good relationships with these peers is important, and losing tools to cement these bonds would be a shame.

Second, leaders need to be able to discuss lots of things with each other. There is evidence that people may find some outcomes so distasteful that they would find it unbecoming if leaders even debated the issue and considered it seriously. For example, a university leader might need to consider a variety of options to cut costs. Faculty members might believe it unacceptable to close down a department or program. But leaders should not be penalized for considering all options, even ones that some people may object to on moral grounds. It is impossible to make good decisions in an organization without questioning deeply held assumptions.

If private conversations are routinely leaked, leaders may have concerns about discussing potentially controversial policy decisions, and this may ultimately hamper decision-making at the organization.

For this reason, a leader can express regret that a conversation intended to be private was leaked, but they should stop short of apologizing for having private conversations.

#28236. Your AI story has an expiration date

A biotech or SaaS company wants to be seen as an AI company. A health company wants to be seen as a tech company. Some have earned the label. Your story can run ahead of your business. That is what vision is for. But it can’t run ahead forever. A good story sets expectations. If the business doesn’t hit the expectation, however, the market responds in many ways: a fall-from-grace headline, a disengaged investor, or a stalled deal.

THE GAP HAS A SHELF LIFE

I call the distance between your vision and your execution “the gap.” Opportunity and disaster both live there. How long you can stay in the gap depends on how many people are watching.

A young company in stealth mode gets plenty of room to maneuver. A well-known brand gets very little, because reporters, analysts, and competitors track every claim. Early on, the story is nearly all you have. Later, especially once you’re public, people start reading the receipts, such as partnerships that were really one-off pilots or R&D spending that never became a product. Wins extend your runway. Big claims with no wins shorten it, and eventually you’re in a crisis.

Right now, that room is smaller than usual. Reporters are tired of AI hype, and the public is uneasy as well. Even as of mid-2023, Pew Research found that 52% of Americans were more concerned than excited about AI, while only 10% felt genuinely excited. The SEC chair warned against “AI washing” in late 2023, and the agency brought its first two AI-washing cases forward in 2024. Since then, a steady stream of related cases has followed.

When the gap gets too wide, external forces close it for you. WeWork pitched a community movement while making its money renting office space; in 2018, Fast Company asked whether WeWork could be worth $40 billion. It peaked at $47 billion in 2019 and filed for bankruptcy in 2023. More recently, Apple agreed to a $250 million settlement over how it marketed delayed features. The more attention you have, the faster someone else closes the gap for you.

Repositioning is grounded in proof. Without that proof, it is just a costume. Before you claim a new category, ask your team a few questions:

  • Who on our leadership team or advisory board has built this kind of business before?
  • Which customers use the product today, and will they say so on the record?
  • What would a skeptical reporter find after 10 minutes of searching your company or execs in Google or an LLM?
  • Could we let someone see how the product works without a human guiding the demo behind the scenes?
  • If we took the word “AI” out of our pitch deck, would there still be a business worth writing about?
  • What is our next proof point, and when does it land?

The answers make up your paper trail: people who validate you, customer data that backs you up, and a clear account of the problem you’re solving. A costume has none of that.

The gap can also run the other way, with the technology ahead of the story. Then the job is helping the narrative catch up.

DO THE WORK FIRST

Bill Walsh, who won three Super Bowls as the coach of the San Francisco 49ers, wrote a book called The Score Takes Care of Itself. He argues that if you focus maniacally on preparation, details, and quality, the desired result will follow. The same goes for your story. If you do the work, category leadership and a higher valuation usually come next.

If you’re a CEO or a communications lead, check your own paper trail before a reporter or a regulator does it for you. Ask your team for proof and verify it yourself. Storytelling is my business, so I’m telling you the story only goes so far. Mind the gap.

#28241. What AI leaves out of the answer still counts

There’s a contradiction emerging in how publishers get paid when AI uses their content. The licensing deals that OpenAI, Meta, Amazon, and others have been signing these past few years appear to be slowing down, at least for the publishers still waiting on one.

Publishers are speaking about this openly. Digiday hosted a London town hall recently, and one publishing executive said discussions with AI companies have slowed down. Also, Katya Gorchinskaya, a Ukrainian journalist and media consultant who built J·Index, a database of thousands of AI implementations in newsrooms, separately told the Reuters Institute for the Study of Journalism that the market for deals with model makers is effectively closed.

At the same time, AI demand for content continues to go up. I recently spoke with Jonathan Roberts, chief innovation officer at People Inc., for The Media Copilot podcast, and he revealed that the number of different bots that try to scrape content from the company’s media properties (including People, InStyle, and Investopedia) now numbers in the tens of thousands every day. The company blocks all but 38 of them. At that Digiday London event, Fiona Spooner, managing director of consumer revenue at the Financial Times, said one trial account tried to access about a million articles in eight hours from 700,000 IP addresses.

I also see this in my GEO client work: the media properties often start from the position that having bots hammer your site all day is cost-prohibitive, so they block them outright. It makes sense, but if the end goal is to monetize your content in AI systems, the slowdown in licensing agreements suggests an all-or-nothing stance won’t give you much leverage.

All of this points to an evolving approach to payment: metered pricing. The industry has already been moving in this direction, but the question that doesn’t yet have a clear answer is what those meters should measure.

Paying for what gets used

Metered pricing has been around for a while. TollBit was one of the first to offer a “pay per crawl” model, directing bots to a gate where they could elect to pay a price set by the site, or go away (the company says its technology is now installed on more than 7,000 publisher sites). Cloudflare followed suit last year with a fanfare announcement that it would block AI bots by default for new sites on its network and provide the tools for publishers to charge by the crawl.

Things have evolved since then. There’s now more energy behind a “pay per use” model, meaning a content provider would only get paid when their content contributes to an answer, not at the moment it’s scraped. Cloudflare itself made that switch in July, with Ceramic.ai and You.com as its first partners, and Google and Microsoft are testing similar models. Cloudflare’s program is still in beta, but Lara Cohen, Cloudflare’s VP of strategic partnerships for media, creators, and AI, told me the company is working toward a system that alerts publishers when a buyer wants their content and lets them accept, decline, or negotiate.

The logic is informed by data: According to research from AirOps covering more than 548,000 pages, only about 15% of what ChatGPT retrieves ends up in its final answers. This is intuitive and matches human experience: When you do research to inform a report, you don’t typically use all of it.

However, we should be careful of stretching the stat too far: Just because chatbots cite only 15% of what they look at, that doesn’t mean the 85% left out is worthless. In fact, uncited sources still shape answers. An Ahrefs study of 1.4 million prompts found ChatGPT leans heavily on Reddit to understand topics while rarely giving it credit. That material might also be exactly what’s needed for a different query, so there is value in having it available.

This is why, when determining value (and thus payment), who’s paying is as important as how much. If it’s an AI app answering a user’s question, it only wants to pay for what’s used. If it’s whoever builds the index that app draws on, there’s value in having the widest corpus of content available.

There’s actually a third party here: the middleman. And the question is even more relevant for them. As I’ve explored before, a whole industry of AI data brokers has emerged over the past couple of years, with hugely valuable companies like Exa, Parallel, and Tavily leading the pack. These companies crawl the internet, then sell access to the corpus to buyers—which are often AI developers. Parallel, valued at $2 billion after a $100 million round in April, says more than 100,000 developers use its tools, at companies like Harvey, Notion, and Opendoor.

Roberts doesn’t think much of the business model. “These businesses take content from the internet for free and sell it for money,” he told me. “They do not create things, they resell things.”

Pricing varies, but they bill customers by the request, which amounts to charging per delivery. Exa charges $1 for every 1,000 pages of full text, and Parallel’s Extract is $1 per 1,000 URLs. In publisher terms, that’s about a tenth of a cent per article.

Some of the services don’t pay publishers at all, but that’s starting to change. Since May, Parallel has partnered with several publishers, including The Atlantic, Fortune, and PR Newswire, on payments through a program called Index. The payouts depend on the measured value of the publication’s contribution to any work Parallel’s agent does on behalf of customers. That incentivizes unique, hard-to-replace content, since it’ll earn more.

The case for an index fee

Although the market for middlemen clearly needs more structure, Parallel’s approach is a real step toward the sophisticated payment system the industry needs. That said, it’s one part of an economy with several layers. Assuming the system can scale, paying publishers only when their content is used is a tough sell since it gives them nothing up front, and it doesn’t address what I mentioned earlier: the value of having the content in a larger corpus in the first place.

For example, say you had a query about a company’s layoffs, and the agent looks at three sources: Source A, an original report with the layoff numbers, which nobody else has; Source B, a wire story that repeats A’s numbers; and Source C, background on the company’s finances. The agent would likely use A, discard B, and maybe lightly incorporate bits of C. Money would flow accordingly.

But B is still valuable to validate Source A, and it’s important to have in cases where there is no Source A. And the next time, Source B might be the one with the original report. To incentivize the widest number of sources, a nominal, flat index fee (not the same as pay-per-crawl) could go a long way toward convincing publishers to participate in the broader system.

That’s less hypothetical than it sounds. Cohen told me that on Cloudflare’s platform, each buyer defines “use” for itself: “Some define this as when content is indexed, while others define it as when content is used to generate answers.” In other words, some buyers are already paying for the library.

As we’ve seen with the bigger licensing deals, this kind of system might be difficult to scale, but that can be addressed by scaling the fee to how much demand there is for a publisher’s content, not how big the publisher is. That’s important because smaller publishers can punch above their weight for the right query. Cohen said the biggest lesson from pay per crawl’s first year was “the tremendous value of long-tail, smaller publishers’ content,” especially local news. “If I’m asking ChatGPT what’s happening today in Duluth, Minnesota, there’s probably only one or two local news sources to pull that information from.” A small paper with no competition is Source A for its whole town.

TIME’s Mark Howard has seen evidence of the library’s value, too. He told me the models appear to store what they scrape, since some TIME articles get more AI referrals than citations, something that shouldn’t happen. And most of the agent crawls TIME sees are of archive stories more than a year old. The library is getting used whether or not anyone pays for it.

Roberts pointed to Spotify as a good analogy for what the industry currently lacks: “We’ve basically got 18 Napsters of content, but there’s no Spotify.” Spotify is actually a great model for this system: It pays rights holders based on their share of streams, but its deals with the major labels have included large advances and guaranteed minimums. A leaked 2011 contract with Sony, for example, showed up to $42.5 million in advances over three years.

In the case of the media, the middlemen would pay publishers a nominal amount for inclusion, then the real money comes in as their content provides actual value for customers.

Google holds the meter

It’s a solid model, but it doesn’t necessarily translate from the “middlemen” market to the mass market. OpenAI already has many licensing deals in place and doesn’t seem interested in other approaches. Perplexity experimented with rev-share models (an ad revenue share in 2024, then Comet Plus, which sends 80% of subscription revenue to participating publishers), but they haven’t had much effect. And the biggest fish, Google, is unique: It’s recently introduced a pilot called News AI for publishers to collect payments for use in Gemini, AI Overviews, and AI Mode, but the pricing is a total black box, and since it has all the leverage, there’s no reason to think that will change.

Which brings it back to the meters. The industry is finally building them, and that’s real progress. But a meter that only counts answers will always undervalue the library, and the library is what makes the answers any good. If publishers are going to keep feeding these systems, someone has to pay for the pantry as well as the ingredients that end up on the plate. Roberts has a simple test for whether the price is right: “If we would create new content for this market, then the pricing is right. If we would not create new content for this market, then the pricing is wrong.” By that measure, we’re not there yet.
